# Рабочий план перехода к реализации

Обновлён 14 сентября 2026 по alpha.12. Это последовательность результатов,
не вторая доска задач. [Основания и пробелы](implementation-readiness.md).
UI уже достаточно развит для подключения к данным; автономный runtime ещё отсутствует.

## 0. Подготовить проверяемый фундамент

- Закрепить текущую архитектуру, модель, карту экранов и версии зависимостей.
- Включить host.ts в обычную проверку TypeScript, проверять все entrypoints.
- Обновить тестовый Vitest до исправленной совместимой ветки отдельным изменением,
  проверить SDK harness; не использовать npm audit fix --force.
- Определить поддерживаемую Node-базу и CI; проверить host shims с BB, а не
  приравнивать devDependencies к runtime браузера.
- Устранить/изолировать невалидную nativeSkillRoots конфигурацию ACP в тестовой
  среде, чтобы проверялся именно выбранный провайдер, а не его неявная замена.

Готово, когда чистая установка по lock проходит entrypoint typecheck, unit/harness,
сборку, загрузку; версии и ограничения воспроизводимы. Текущий аудит уже прошёл
37 тестов и typecheck; он не заменяет перечисленные незакрытые пункты.

## 1. Постоянные данные и рабочий интерфейс без запуска агентов

Ввести stable ID, revision и миграции Agent/Version, Department/Membership,
ProjectBinding, Job/Dependency, Artifact/Version, Activity. Реальные данные и
деморежим разделить. Сервисы команд используют одну транзакцию для состояния
и истории. Подключить по очереди каталоги → задача → файлы → входящие.

Критерии:

- Создать проектную привязку, отдел, сотрудника и задачу; refresh и restart
  сохраняют их связи, файлы и историю. Имена можно менять без потери связей.
- Два открытых окна не затирают правки: конфликт revision виден пользователю.
- Список/канбан/счётчики/входящие используют одну выборку; фильтр и возврат
  к очереди сохраняются. Нет демозапуска RUN-204 у чужой задачи.
- Документ открывается по клику в закрываемой вкладке BB, свойства задачи
  временно скрыты; YAML свёрнут. После reload файл/версия корректно восстановлены.
- Изменение файла создаёт версию, а не переписывает принятый результат.
- Проверены миграция alpha.12, backup/restore и изоляция данных проектов.

## 2. Доказать изоляцию одного исполнителя

Можно исследовать независимо от CRUD, но это обязательный gate любого запуска.
Начать с одного установленного CLI на Mini: один разрешённый MCP и skill,
два отличающихся профиля. Проверить видимый каталог и попытки запрещённых вызовов,
resume, смену профиля и параллельные сессии. Проверить обход через shell/BB CLI,
native roots и deferred tools. Сохранить доказательства и capability matrix.

Готово: разрешённое работает, запрещённое не выдаётся и не вызывается. Если
публичного SDK не хватает — оформить минимальное изменение core/адаптера с
контрактными тестами. До исправления execution остаётся unavailable. Интерфейс
галочек не считается результатом этапа.

## 3. Один полный ручной цикл

Зависит от 1 и 2. Назначение → immutable context snapshot → lease → скрытый Run →
вопрос → структурированный ответ → файл результата → review версии → done.
Один выбранный провайдер/host, без автоматического резерва. Сохранение и
назначение — отдельные действия. Нативный interaction ответ связан с исходным ID.

Критерии:

- Состояния running/waiting_input/review/failed различимы и имеют следующий шаг.
- Вопросы работают табами «Вопрос 1…», далее/назад/отправить; повторный клик,
  закрытие запроса другим окном, expiry и secret request обработаны корректно.
- idle не закрывает задачу. Review принимает конкретный hash/версию, возврат
  создаёт доработку с замечанием. Комментарий сам по себе агента не будит.
- Stop подтверждён BB; handoff новому сотруднику/модели создаёт следующую попытку
  с явным контекстом и освобождением папки, сохраняет предыдущую историю.
- Проверены сбои до/после spawn, перед bind, во время записи файла и после resolve.
  Неопределённый исход показан как сверка, не повторён как новая работа.

## 4. Отделы и событийная работа

Единый registry EventDefinition, envelope/inbox, rule versions, matches/outbox,
dispatcher и reconcile. Сначала цепочка исполнитель → проверяющий → следующий
отдел. Проект/права/версии сохраняются в дочерних заданиях. Менеджер получает
каталог подключённых отделов, не весь глобальный штат.

Готово: повторное событие не создаёт второй Run; зависимости не цикличны;
технические retries, возвраты review и глубина делегирования ограничены;
обновление правила не меняет уже принятый intent; пауза запрещает новые старты.
Нативные и собственные события имеют понятное название и системный ключ.

## 5. Расписания, webhook и необязательные интеграции

[Контракт автоматизаций](automation-architecture.md): observe → approve → auto.
Сначала воспроизводимая локальная проба и durable приём, затем действия.
Webhook: source binding/auth/signature, schema, лимиты, dedup, условия, истории
доставок и ручной replay. Cron: timezone/DST, пропуски, queue/skip/latest и
предпросмотр следующих дат. Ни один источник не обходит launch gate.

Telegram подключается при наличии capability и opt-in: уведомление или ссылка
на вопрос через существующий bridge/outbox, polling receipt и понятная ошибка.
Проверить отсутствие/старую версию/отключение bridge, неизвестный исход доставки,
раздельную паузу новых сообщений и уже принятой очереди. Обратные ответы Telegram
и дополнительные события добавлять только по объявленному контракту адаптера.

Готово: закрытый браузер не мешает работе, рестарт BB не теряет принятую задачу,
дубликат/повреждённая подпись не запускают агента, missed schedule ведёт себя
по политике. Нет отправки секретов или бесконечной цепочки уведомлений.

## 6. Переносимость и пилот первой версии

Проверить первый запуск без личных IDs/путей и без Telegram, затем с настроенным
bridge. Подсказки показывают недостающую конфигурацию, а не пустую форму.
Резервный CLI включать только после его самостоятельной проверки совместимости
и изоляции: установлен ≠ авторизован ≠ доступна модель ≠ разрешён fallback.
Qwen/Kimi не обещаются заранее; источник списка — актуальные провайдеры BB.

Пилот: пользователь без CLI создаёт поручение, отвечает на вопрос, открывает
материал, принимает/возвращает версию, меняет исполнителя и понимает сбой.
Проверить узкую панель/desktop, клавиатуру, отсутствующие данные, задержки,
длинные названия, загрузку/ошибки, историю, лимиты, backup/restore и retention.
Снимок демонстрации не считается проверкой рабочего процесса.

## После первой версии

Сложный визуальный редактор DAG, двусторонние ответы Telegram, расширенные
пакеты отделов/шаблонов, массовые операции, множество новых CLI и полноценная
многопользовательская модель — отдельные этапы по результатам пилота.
Существующие справочники процессов могут быть импортируемым материалом; их
этапы/поручения не становятся исполняемыми правилами без валидации этого контракта.

Ближайший показываемый результат: сохранённые сотрудник, отдел, задача и файл,
переживающие перезагрузку. Следом — один доказанно ограниченный ручной запуск.
