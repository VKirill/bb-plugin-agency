# Этапы

1. **Каркас (этот этап):** точки входа, разделение модулей, сохраняемый notify,
   честная страница состояния, SDK harness, сборка. Реальная установка отдельно.
2. **Изоляция:** один CLI, один MCP/skill; посторонние не видны/не вызываются,
   повторный старт и параллельные профили не расширяют доступ. Выбрать адаптер или
   расширение core. До доказательства ни один trigger не запускает сотрудника.
3. **Вертикальный цикл:** профиль+задача+снимок+скрытый worker+артефакт+stop;
   сверка после сбоя spawn и после restart.
4. **Отделы и доски:** собственные сущности, менеджер проекта, каталог ролей,
   проверяемая декомпозиция и связи заявок между отделами.
5. **Событийная оркестрация:** inbox/outbox, правила, повторная доставка,
   ревью конкретной версии, bounded retries, запрос человеку.
6. **Расписания и интеграции:** cron/timezone, пропуски/DST, ручное уведомление,
   workflow-worker, проверяемый webhook. История и пауза в UI.
7. **Пилот:** реальный процесс, закрытый UI, перезапуск сервера, backup/restore.

При обновлении с alpha.1 не исполнять накопленные пробные уведомления без явного
решения владельца. Полномочия projectId и источника проверяются до создания Run.

## Уточнение по пользовательским сценариям

Для вертикального цикла обязательны понятный бриф, вопрос/ответ и проверка
версии результата. Для профилей — пробная смена модели и независимый откат.
[Сценарии выступления](video-scenarios.md), [общение в задаче](task-interaction.md).
Шаблоны первого запуска и проверка на новичке входят в пилот, а не считаются
выполненными по наличию прототипа.

Для этапов 3–6 обязательны контракты [автоматизаций](automation-architecture.md)
и [сборки контекста](instruction-context.md). Перед включением webhook: observe-only
с перезапуском и повторной доставкой; затем согласование; затем автодействие после
доказанной изоляции. Критерии проверки и границы первой версии находятся там.
