# Ревью Агентства: Multica, план и интерфейс

Дата: 13 сентября 2026. Основа — alpha.8; исправления UI включены в alpha.9. Владелец: thr_2sgqe4rmmd. Проверка на Mac mini. Это ревью продукта и контракты дальнейшей реализации, не заявление о готовности автономной системы.

## Вывод

BB и Multica пересекаются: запускают CLI-агентов, работают с машинами, моделями, контекстом и историей. Но считать их одинаковыми продуктами было бы неточно. В Multica агент — участник рабочего пространства, а назначения, обсуждения и автоматизации организованы вокруг задач и запусков. В нашей конструкции BB обслуживает машины/провайдеры/чаты и расширения; Агентство должно собрать связный пользовательский процесс над этим фундаментом. Отдельную копию daemon BB не строим.

[AGENTS.md](http://AGENTS.md) — источник инструкций. Он сам не обеспечивает доставку поручения, блокировку рабочей папки, возобновление, транзакции и приёмку результата. Галочки и JSON тоже не доказывают изоляцию. Главная незавершённая часть — исполняемый контракт между намерением пользователя и конкретным Run.

Источник сравнения: [Multica Agents](https://multica.ai/docs/agents), [Runs](https://multica.ai/docs/tasks); для BB — [сверенный SDK](bb-api.md).

## Что полезно перенять, а где наше решение отличается

| Возможность Multica | Решение для Агентства |
| --- | --- |
| Участник и его runtime имеют разные состояния | Профиль включён / машина доступна / загрузка. Одно «Доступен» недостаточно |
| Squad сначала получает лидер | Отдел получает одну корневую заявку; руководитель назначает подзадачи, не запускает весь штат |
| Предпросмотр получателей при упоминании | Перед отправкой показать, кто будет вызван и почему. Обычная заметка у нас остаётся без запуска |
| Последовательные комментарии объединяются для занятого агента | Доставка обновлений в текущую попытку или одну следующую; не spawn на каждую строку |
| История попыток непосредственно у задачи | Сохраняем правую панель; активное видно сразу, прошлое раскрывается |
| Автопилот по расписанию/webhook, отдельная история доставок | Сохраняем наш Inbox/Rule/Intent. Доставка, выполнение и бизнес-результат имеют разные статусы |
| Создание агента из минимального набора полей | Первая версия: шаблон роли → инструкции → исполнение → тест. AI-builder позже |
| Методы оформляются в skills с источником | У нас BB-каталог + закреплённая версия навыка. Обновление после просмотра изменений |

Основания: [Squads](https://multica.ai/docs/squads), [упоминания](https://multica.ai/docs/mentioning-agents), [создание агента](https://multica.ai/docs/agents-create), [Skills](https://multica.ai/docs/skills). В Multica инструкции squad предоставляются руководителю; у нас правила отдела планируются также для исполнителей с явным указанием области. Это осознанное различие, не повод переписать правила наследования.

Multica также предлагает режим автоматизации с созданием задачи или только запуском, предпросмотр ближайших дат, журнал доставок, причины пропусков и контролируемый повтор webhook. Для нас первый режим достаточен на старте; наблюдение/согласование и версия результата остаются частью своего контракта. [Autopilots](https://multica.ai/docs/autopilots).

## Пробелы и противоречия нашего плана

P0 — закрыть до первого реального автономного процесса; P1 — после рабочего вертикального сценария; P2 — расширение. Ниже критерии функций, а не вторая доска.

| Приоритет / пробел | Что уже было | Что уточняем / как принять |
| --- | --- | --- |
| P0. Владение данными и стабильные ID | Типы домена перечислены, UI использует имена | AgentId, DepartmentId, ProjectId, membership. Имя — отображение. Переименовать отдел/сотрудника: задания, правила и история сохраняют связи |
| P0. Связь проекта Агентства с BB | Упомянут ProjectBinding | Один binding содержит BB projectId + environmentId + hostId и корень файлов. Отдел общий, контекст проекта на конкретном заказе. Офлайн/недоступный binding блокирует старт с объяснением |
| P0. Состав команды | В UI и agent.department, и members отдела | Единственный источник — membership с ролью. Один сотрудник может участвовать в нескольких отделах. Лидер входит в состав. Смена лидера не переназначает уже работающих автоматически |
| P0. Изоляция и совместимость | Уже хорошо описана, это не новый пункт | Матрица provider × host × skills/MCP/shell/resume. Неизвестное ≠ поддерживается. Пока нет подтверждения — старт закрыт. Импорт JSON валиден отдельно от его совместимости |
| P0. Поведение назначения/комментария | Типы общения и права есть | Таблица ниже задаёт создание Run, ответ во время работы и дедупликацию. Никаких скрытых запусков от просмотра или пометки прочитанным |
| P0. Пауза/отмена/архив | Описаны фрагментами | Разделить паузу новых работ, остановку конкретного Run и архив. Перед архивом показать активные зависимости; без молчаливой отмены/переназначения |
| P0. Занятая рабочая папка | Есть лимиты агентов, но не контракт общей записи | Для in_place ресурсный lease по host + нормализованному корню. Независимые read-only можно параллельно, запись сериализуется. Состояние «Ждёт рабочую папку», владелец блокировки и причина видимы |
| P0. Возврат к работе после ошибки | Reconcile и bounded retry есть | Разделить технический повтор, продолжение диалога и новую версию результата. Auth/config/quota не повторять бесконечно. При неизвестном исходе не выполнять внешнее действие повторно |
| P0. Сохранение/несколько вкладок | Контекст snapshot есть, UI в памяти | Server revision + optimistic concurrency, конфликт с сохранённым черновиком. Изменение профиля не меняет snapshot текущей работы. CRUD и загрузка должны предшествовать workflow |
| P0. Файлы и версии результата | Artifact/Review есть | Постоянный ID, версия/hash, MIME/size, автор, доступность и ACL проекта. Старые ссылки остаются читаемыми; отсутствующий файл не заменяется демофайлом. Приёмка фиксирует версию |
| P0. Вопрос и уведомление | «Просмотр ≠ решение» уже записано | Уточнить Notification(read/archive) отдельно от Question/Approval(open/resolved). Исчезновение из непрочитанных не снимает блокировку |
| P1. Первый запуск без терминала | Сценарий из видео уже есть | Явный мастер с состояниями: материалы готовы, CLI готов, разрешения проверены, пробная задача принята. Три примера поручений заполняют редактор без отправки |
| P1. Копирование/архивирование профиля | Версии/откат есть | Копия роли без реальных секретов; перечислить унаследованное. Сначала проверка нового профиля. Архив сохраняет авторство старых комментариев |
| P1. Обновление знаний/навыков | Источники/предложения есть | Proposal → review → accepted/rejected; кто утвердил, версия и затронутые сотрудники. Обновление source не перезаписывает местные правки без сравнения |
| P1. Длительная автоматизация | Ретраи/cycle limit есть | Circuit breaker по серии сбоев; единичное уведомление владельцу, объяснение автопаузы. Порог задаётся проектом, не копируем чужое значение без наблюдений |
| P1. Выбор вида/поиск | Фильтры и будущие saved views есть | Один query для списка/канбана, сохранять строку поиска/сортировку/позицию при возврате; ссылки на конкретное событие/файл |
| P2. Run без задачи | Пока вся работа через Job | Для v1 оставляем задачу как обязательный след. Режим только Run для лёгких проверок возможен позднее, с отдельной историей, квотами и тем же аудитом |

Multica уже различает типы попыток, состояния runtime и ожидание рабочей папки; это полезные ориентиры для нашего in_place процесса, а не измерение его скорости. [Runs](https://multica.ai/docs/tasks).

## Единый контракт взаимодействия для первой версии

| Действие | Результат в системе | Что показывает UI |
| --- | --- | --- |
| Написать заметку | Comment, без Run | «Комментарий. Исполнитель не запускается» |
| Передать в работу | Assignment + Intent → Run после проверки | Получатель, проект, входы, причина ожидания |
| Обратиться к агенту в обсуждении | Explicit invoke/commentId, без смены владельца Job | Предпросмотр адресатов и кнопка отправки поручения |
| Ответить на открытый вопрос | Resolve question + follow-up intent, один раз | Ответ принят; какой этап продолжится |
| Дописать во время работы | Inbox update с ID; очередь для следующего хода либо поддерживаемый send | «Доставлено в текущую работу» или «Будет передано следующим шагом» |
| Принять результат | Review(artifactVersion) + разрешённые зависимости | Принята версия N; следующий отдел/этап |
| Изменить исполнителя | Меняется будущее назначение; текущий Run остаётся явно видимым | Выбор: дождаться или отдельно остановить текущую работу |
| Пауза | Запрет новых назначений, текущие не отменяются | Причина и очередь ожидания |
| Остановить Run | Cancel intent, подтверждение от runtime/reconcile | «Остановка запрошена» до фактического исхода |
| Повторить после сбоя | Новая попытка с ссылкой на прежнюю; эффект предварительно проверяется | Что повторится и что уже сделано |

Наш выбор: автоматического вызова исполнителя от любого обычного комментария нет. Пользователь видит действие до отправки. В Multica маршрутизация комментариев может вызывать агента; оттуда берём предпросмотр и объединение обновлений, сохраняя понятный режим заметки. [Mentions](https://multica.ai/docs/mentioning-agents).

Основа UX: установленный ui-review, [DESIGN.md](http://DESIGN.md), общие компоненты BB. Главный критерий — объяснимый путь пользователя, а не визуальное сходство с конкурентом. Нативные Picker, Dialog, Input, Switch и theme tokens сохранены.

## Очерёдность реализации после ревью

1. **До автономии:** доказать изоляцию одного CLI; подтвердить API/права доступа.
2. **Постоянные сущности:** ID/membership, ProjectBinding, CRUD/revision, версии профиля, артефакты, загрузка/ошибка/конфликт UI.
3. **Один законченный сценарий:** вручную поставить → исполнитель → вопрос → ответ → версия результата → ревью → принятие. Все события имеют одну историю.
4. **Надёжность этого сценария:** offline, общая папка, потеря связи, повтор, reload, возврат результата, два одновременных ответа, восстановление backup.
5. **Оркестрация:** руководитель/подзадачи/передача; затем события/cron/webhook, сначала наблюдение, далее согласование и автоматическое действие.
6. **Удобство:** шаблоны первого запуска, сохранённые виды, поиск истории, подписки, копирование профиля и управляемое обновление знаний/skills.

Критерий пилота: человек, не участвовавший в разработке, выполняет сценарий 3 из UI без терминала и умеет понять/исправить хотя бы один сбой из сценария 4. Измеряем места обращения за помощью и ошибки, а не заявляем «user-friendly» по числу экранов. Расширенный AI-builder и запуск без Job не блокируют этот пилот.
