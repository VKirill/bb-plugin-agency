## Сможет ли работать обычный пользователь

В записи спикер — технический пользователь, который по собственному рассказу
тратит много времени на изучение инструментов. Это не тест доступности системы
для новичка. Наш прототип также пока не доказывает простоту сквозного процесса.

Первый путь должен занимать одну последовательность экранов:
«Выбрать шаблон отдела → подключить материалы → проверить доступы → поставить
тестовую задачу → получить результат». CLI, reasoning, MCP и тонкие лимиты
доступны в расширенных настройках. Профиль показывает человеческое объяснение
каждого доступа, а не только имя сервера. Неподключённые зависимости выявляются
до старта, с конкретным действием для исправления.

Повседневный путь: краткий бриф → предлагаемый план → работа → вопрос/ответ →
результат → принять/вернуть. Служебные промпты, пути и команды остаются в
диагностике. Для пользователя смысл текущего шага важнее количества агентов.

## Приёмка перед обещанием автопилота

Один пилот, сопоставимый с примером спикера: входящие данные → скрипт обработки →
проверка → черновик результата → решение человека. Выполнить без терминала из UI.
Повторить с ошибкой, отсутствующими данными и перезапуском BB. Затем дать сценарий
человеку, не участвовавшему в разработке, и записать где потребовалась помощь.
35 сотрудников заранее не нужны: достаточно руководителя, исполнителя и критика.
