# Проверка готовности к реализации

14 сентября 2026 · исходная версия alpha.12 / a18c3b6 · Mac mini.

## Бриф и первая версия

Для владельца BB, который хочет управлять AI-сотрудниками через понятные задачи.
Проблема: инструкции, инструменты, запуски и результаты разрозненны; невозможно
по одному экрану понять, кто работает, что нужно от человека и какая версия готова.

Первый продукт: сохраняемые сотрудники/отделы/проектные привязки, очередь задач,
один контролируемый ручной цикл с вопросом и файлом, затем его событийная и
плановая активация. Используем UI, машины и треды BB. Отдельного агентского сервера,
нового task tracker для разработки или полной копии Multica не создаём.
Наличие похожих экранов BB и Multica не означает одинаковых контрактов исполнения.

не готов: сначала постоянные данные и доказанная изоляция. В документах устранены
расхождения о host entry, каталогах UI, старых вкладках запуска и готовности

## Что нашли дополнительно

1. `host.ts` зарегистрирован в package.json, но пропущен в include tsconfig.
   Добавить в стандартный typecheck на этапе 0. Дополнительная проверка через
   TypeScript API с явно включённым host.ts дала 0 diagnostics; проблема в охвате
   постоянной проверки, не обнаруженная ошибка самого entrypoint.
2. `agency_inbox` допускает только pending и rpc/cli. Для runtime нужны новые
   таблицы/миграции, а не изменение state в текущей схеме. Старые notify не replay.
3. Domain и UI имеют разные состояния и связи по именам. Единый серверный
   контракт должен предшествовать интеграции всех экранов.
4. Документы сейчас записываются на primary host, а не на host привязки заказа;
   map собственного file opener теряется при refresh. Нужен durable artifact resolver.
5. В примере есть фиксированная ссылка RUN-204. Реальные связи искать по Job/Run ID,
   не использовать fallback на чужой пример.
6. Telegram preference пока рассчитана на одну проектную привязку; bridge имеет
   личные ограничения. До переносимого выпуска — per-project настройки и проверка
   отсутствующего/несовместимого адаптера. Никакой обязательной Telegram-зависимости.
7. Два moderate audit findings относятся к одной проблеме тестового Vitest/mocker.
   Производственный audit чист. Нужен отдельный проверенный major upgrade тестового
   стека; версии и первичный источник в [инвентаризации](dependencies.md).
8. BB CLI сообщает о невалидном nativeSkillRoots custom ACP entry. Это проблема
   среды вне репозитория Agency; до isolation spike проверить ожидаемый provider
   и отсутствие неявного fallback. Конфигурация в этом ревью не менялась.
9. 37 тестов покрывают каркас/парсеры/настройки, но ещё не покрывают автономный
   процесс, межпроектный доступ, отказы, миграции и конкурирующие ответы.

10. Доступ внешнего webhook sender к маршруту BB Connect без браузерной cookie
    и выбранный secure storage для подписи нужно проверить перед HTTP-этапом.
    Наличие http.route не доказывает доступность извне.

## Проверки этого ревью

- package.json ↔ package-lock.json ↔ npm ls: прямые установленные версии записаны;
  зависимостей invalid/extraneous не обнаружено.
- `bb plugin types --check`: SDK pin/host 0.4.87 совпадают; отдельно отмечено ACP warning.
- `npm run typecheck`: прошло в текущей области tsconfig.
- `npm test`: 37/37 в пяти файлах, Vitest 3.2.7.
- `npm audit --omit=dev`: 0; полный audit: 2 moderate, 0 high/critical.
- Проверены текущие точки регистрации и публичные SDK declarations; таблица API
  различает существующую возможность и её подключение в плагине.
- Повторного UI обхода и запуска worker в этом документальном ревью нет.
  Live UI alpha.12 проверялся в предыдущем изменении; пакеты/код не обновлялись.

## Что не решается догадкой

Способ строгой изоляции каждого CLI выбирается по эксперименту, а не по сходству
с Multica. При недостатке SDK результатом будет конкретный запрос/патч платформы.
Совместимая исправленная версия Vitest и минимальная Node-база выбираются после
проверки harness/build. Обратные Telegram answers требуют отдельного контракта.
Эти вопросы технические; повторный бриф владельца для старта CRUD не требуется.
