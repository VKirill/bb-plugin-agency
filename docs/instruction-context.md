# Инструкции разных уровней

Проект решения, 2026-09-13. Сборщик контекста и принудительная изоляция ещё не
реализованы. Поля прототипа сами по себе не управляют реальным агентом.

## Что где задаётся

| Уровень | Содержимое | Пример |
|---|---|---|
| Проект | Цель, аудитория, факты, бренд, допустимые действия и канон материалов | SelfyStudio, русский язык, подтверждать рекламные обещания |
| Отдел | Процесс, роли, порядок передачи, критерии приёмки отдела | Автор → независимый редактор → возврат до двух раз |
| Сотрудник | Специализация, методы, инструкции роли, skills/MCP и среда | Копирайтер: ru-text, чтение документов, без публикации |
| Задача | Конкретный результат, исходные материалы, срок и дополнительные критерии | Оффер услуги, один Markdown-файл, три варианта заголовка |
| Запуск | Зафиксированный набор предыдущих версий + текущее поручение | Анна v3 / редакция v2 / проект v5 / задача v4 |

«Порядок работы» описывает шаги. «Критерии приёмки» описывают наблюдаемый результат.
В UI это разные поля, с примерами. Критерии отдела дополняются задачей; результат
не считается принятым только потому, что агент написал «готово».

## Сборка контекста

1. По собственным ID определить задачу, проект, отдел, назначенного сотрудника.
   Маршрут и полномочия проверяются сервером, не из текстового поля webhook.
2. Загрузить актуальные опубликованные версии правил, приостановки и grants.
3. Проверить противоречия в структурированных полях: запрещённое действие,
   несовместимый формат/язык, отсутствующий нужный инструмент или материал.
4. Вычислить права и доступные источники; затем собрать разделы контекста:
   цель/канон проекта → процесс отдела → роль сотрудника → бриф задачи → текущий
   этап и критерии → материалы/подтверждённые факты с источниками.
5. Создать immutable ContextSnapshot: IDs/версии/хеши и эффективные возможности.
   Run хранит ссылку на snapshot. В UI доступен «Контекст запуска»: итоговый текст,
   источник каждого блока, выбранные MCP/skills и причины исключения остальных.
6. Секреты не подставляются в промпт; агент получает авторизованный инструмент.
   Вложения, сообщения и память находятся в разделе данных, а не системных правил.

Это не просто конкатенация длинных промптов. Бюджет контекста известен заранее:
ограничения/бриф/критерии не обрезаются молча; дополнительные документы подгружаются
из разрешённых источников. При нехватке места сборка останавливается с объяснением.

## Приоритеты и конфликты

Модель не должна сама выбирать между всеми текстами «что ниже, то важнее».
Порядок основных платформенных инструкций BB/CLI остаётся платформенным.
Плагин задаёт продуктовые правила внутри разрешённого платформой контекста.

- Полномочия: пересечение явных ограничений платформы/host, проекта, отдела,
  сотрудника и задачи. Unset означает наследовать ограничение; явный пустой
  allowlist означает запретить всё. Профиль сотрудника задаёт выбранный набор,
  остальные уровни могут его сузить. Никакой текст не расширяет этот набор.
- Общие требования проекта действуют для каждого отдела. Отдел задаёт способ
  исполнения, сотрудник — профессиональные методы; задача уточняет результат.
- Настраиваемые значения (формат, язык и т. п.) получают typed поле и признак
  «разрешено переопределение». Тогда более конкретная задача может уточнить поле
  в указанном диапазоне. Hard constraint не переопределяется локальным текстом.
- Если задача просит английский текст, а русский язык отмечен предпочтением,
  можно переопределить с указанием источника. Если русский — обязательное правило,
  это конфликт: попросить владельца изменить правило или бриф.
- Если отдел требует публикацию, а сотруднику не разрешена публикация, он
  готовит материал и передаёт уполномоченному исполнителю; права не расширяются.

Для свободного текста невозможно гарантировать обнаружение всех смысловых
противоречий. Модель может отметить подозрение на конфликт, но не выдавать новые
полномочия. Формальные конфликты блокирует сервер; смысловые попадают в запрос
руководителю со ссылками на спорящие положения. Одобрение фиксирует конкретное
изменение/исключение с областью и сроком, а не скрытый ответ «игнорируй правила».

## Несколько отделов и проектов

Одна задача исполняется в контексте одного проекта и назначенного отдела.
Сотрудник может работать в разных отделах, но каждый Run собирает свой контекст.
Правила всех отделов организации не добавляются в каждый промпт автоматически.

При межотдельной передаче создаётся связанная задача: проект и ограничения
сохраняются, процесс берётся у получателя. Передаются результат/версия, критерии
передачи и ссылки. Частная переписка и весь промпт отправителя не копируются.
Начальник маркетинга не становится начальником редактора только из-за участия
в одном проекте. Поэтому на схеме сплошная линия — структура отдела, пунктир —
координация проекта. Глубокую иерархию отделов и reportsTo добавлять только вместе
с явными связями и проверками циклов; сейчас Group содержит lead + members.

## Изменения во время работы и память

Обычные изменения инструкций действуют для нового Run. Текущий показывает свой
snapshot; нужен явный перезапуск/новый ход с новым контекстом для их применения.
Отзыв доступа/аварийная пауза проверяется на шлюзе инструментов немедленно, а не
ждёт следующего промпта. Если провайдер не поддерживает безопасный отзыв, запуск
останавливается; нельзя обещать динамическое ограничение без проверки адаптера.

Память — подтверждённые знания с source/version/project scope; не новые команды.
Предложение агента изменить канон ждёт принятия владельцем/назначенным редактором.
Запрет скрытого изменения своих прав действует и для CLI/API управления BB.

## Поля и критерии внедрения

PolicyVersion: scopeType/scopeId/version, structured constraints, instructions,
acceptanceCriteria, publishedAt, author. ContextSnapshot: references, compiledText,
capabilities, source list, unresolved conflicts. Дополнения к Run — snapshotId,
policyVersion, reviewArtifactVersion. Черновик отдельно от опубликованной версии.

UI: «Правила проекта», «Как работает отдел», «Критерии приёмки», «Инструкция
сотрудника» с подсказками; предпросмотр контекста после выбора задачи/отдела;
конфликт показывает оба источника и маршрут решения; история изменений и откат.

Приёмка: смена проекта одного сотрудника не переносит чужие материалы; запрет
публикации не отменяется задачей/вебхуком; разные отделы дают разные процессы;
старый Run показывает прежнюю версию; новый — новую; просроченное согласование
не применяется; неразрешённый skill/MCP отсутствует в каталоге и недоступен вызову.
