# UI «Агентства»: карта экранов и прототип

Версия прототипа: 0.1.0-alpha.5. Это предложение интерфейса всех основных частей системы. Основной маршрут: `/plugins/agency/overview`. Изменения примера хранятся в памяти страницы, до перезагрузки. Ни одна кнопка прототипа не создаёт реальный агентский запуск, расписание или задачу Tasks.

## Принципы BB

- Встраивание через `definePluginApp` / `slots.navPanel`, переходы через `useBbNavigate().toPluginPanel`: поддерживаются адреса и история браузера.
- Используются тема, типографика и CSS-токены BB. Нет отдельной дизайн-системы, внешних шрифтов или собственной палитры. Новый прототип создан на React внутри плагина; HTML skill page-prototype исключает live UI и здесь не применяется.
- Buttons/Input/Checkbox/Dialog — штатный scaffold; Select/Tabs/Textarea/Switch/ Table/Badge — компоненты официального реестра `@bb` desktop-v0.43.1. Вендоринг исходников компонентов — предусмотренный BB способ, не импорт приватного @bb/\*.
- `experimental_ProviderModelPicker` — реальный CLI/model/reasoning/service-tier picker, `experimental_PermissionModePicker` — режим разрешений BB. Каталог машин через read-only RPC `uiContext` → `sdk.hosts.list`. По умолчанию Mini, если такая машина присутствует; пользователь может изменить выбор в макете.
- `experimental_NewThreadComposer` на вкладке менеджера — реальный редактор BB, обработчик отправки только показывает сообщение прототипа; spawn не вызывается.
- Markdown и SourceCode — штатные рендереры BB. Для будущей истории реальных запусков использовать ThreadChat, для реальных файлов FileLink. Фальшивые threadId/пути не передаются этим компонентам ради демонстрации.
- Узкий экран: выпадающая навигация, одноколоночные формы, прокрутка вкладок и канбана внутри блока. У каждого действия есть доступное имя, у полей — label. Перемещение канбана мышью дублируется доступным выбором статуса в карточке.

## Общая оболочка

Постоянный индикатор «Прототип», кнопка сброса примера с подтверждением. Локальная навигация: Обзор, Задачи, Сотрудники, Отделы, Проекты, Автоматизации, Входящие, Запуски, Знания, Настройки. В полном продукте эта полоса заменяется обычным состоянием системы; режим предпросмотра профиля остаётся отдельным.

## Задачи

Один набор карточек для двух видов. Статусы: Бэклог, К запуску, В работе, На проверке, Ожидает решения, Готово, Отменено. В рабочей реализации потребуется отдельно различать waiting_input и blocked, даже если доска группирует их вместе.

Канбан: колонка с названием и счётчиком; карточка с ID, приоритетом, названием, проектом, исполнителем и сроком. Горизонтальная прокрутка сохраняет читаемую ширину. Список: таблица задачи, статуса, проекта/отдела, исполнителя и срока. Данные едины.

Карточка:

- Описание: вводные, критерии приёмки, редактирование, обсуждение.
- Подзадачи: состав и зависимости, место добавления дочерней заявки.
- Результаты: файл, версия, проверяющий, принять/вернуть/открыть.
- Запуски: история исполнения и переход к Run.
- История: причинная цепочка действий и переходов.

В прототипе создание задачи, комментарии, смена свойств/статуса и приёмка меняют локальный пример. Подзадачи и файлы показаны как пример с объяснением будущего действия. Не имитируется успешная загрузка несуществующего файла.

## Сотрудник

| Вкладка | Поля / управление |
| --- | --- |
| Профиль | Имя, роль, отдел, доступен/пауза |
| Инструкции | Обязанности, границы, формат результата; схема сборки контекста |
| Исполнение | Машина; единый native picker CLI/model/reasoning/service tier; native permission picker; concurrency; наследование папки проекта |
| Навыки | Поиск, чекбоксы, счётчик, снять все; демонстрационный каталог |
| MCP и доступ | Чекбоксы MCP; терминал; делегирование; границы файлов/сети |
| Проверка | Итоговый выбранный набор, модель, статус изоляции, место тестового поручения |
| История | Черновик, версии, будущая привязка запусков к версии |

В полном продукте карточка также получит версионное сохранение, сравнение с применяемой конфигурацией, связи с проектами и подробную политику доступа. Эти части не следует заменять текстовым «используй только разрешённое». CLI не выбирается из локального массива названий; picker получает актуальные провайдеры BB и сам согласует выбранную модель и её возможности.

## Отдел и проект

Отдел определяет процесс и исполнителей, проект — материалы и бизнес-цель. Менеджер проекта получает каталог только подключённых отделов. Межотдельная заявка сохраняет проект. Канбан на вкладке «Задачи» фильтрует тот же набор.

Реальная привязка к BB project/environment/section и файлам потребует API; сейчас демонстрационные проекты не создаются в BB. В «Менеджере» показан штатный composer для будущего контролируемого запуска. Реальные чат/история должны отображаться через ThreadChat, а не через свой аналог редактора сообщений.

## Автоматизации

Четыре источника: событие/уведомление, cron, webhook, вручную. Триггер события выбирает тему; действие — проект, отдел и шаблон поручения. Ограничения: пропуски расписания, наложение работ, число повторов и защита циклов.

Cron-preview действительно вычисляется cron-parser в IANA timezone. Он не регистрирует расписания BB. Для неверного выражения показывается ошибка. Тест события сравнивает введённую тему и показывает предполагаемый маршрут. Webhook пока показывает будущий точный маршрут и требования авторизации. Работник BB Workflow сможет послать уведомление; сам workflow-скрипт не является долговременной подпиской. Включённое правило на экране остаётся примером.

## Что можно пройти сейчас

1. Задачи → Канбан/Список → карточка → сменить статус → вернуться к очереди.
2. Создать задачу → заполнить название → редактировать вводные/свойства.
3. Сотрудники → Анна → Исполнение → открыть штатный каталог CLI и моделей.
4. Навыки/MCP → выбрать чекбоксы → Проверка → увидеть выбранный набор.
5. Отдел → состав/правила/задачи. Проект → подключённые отделы/Менеджер.
6. Автоматизация → расписание/событие → Проверка → увидеть маршрут или даты.
7. Входящие → задача с ожиданием; Запуски → журнал; Знания → preview/редактирование.
8. Настройки → Диагностика → сброс примера с подтверждением.

## Композиция alpha.4 (заменяет прежние вкладки карточки)

Карточка задачи — единый экран: путь и название, подписанные свойства, Сейчас,
условный результат, описание, реальные дочерние карточки демонабора, исполнители

Все события текущей карточки живут в UI до refresh. Серверного аудита и новых
реальных запусков нет. Правила: [DESIGN.md](../DESIGN.md).

## Alpha.5: все разделы и вложения

Сотрудники/отделы/проекты/автоматизации/запуски — общая компактная таблица.
Профиль сотрудника: Обзор, Инструкции, Исполнение, Возможности, История.
Отдел: Обзор, Задачи, Сотрудники, Настройки; проект: Обзор, Задачи, Отделы,
Настройки, Менеджер. Навыки и MCP сведены в Возможности, параметры отдела —
в Настройки. Home, Inbox, Knowledge и Settings используют ту же шкалу
заголовков, действий и вкладок; у Inbox акцент на запросе решения.

Job: один выделенный блок приёмки, файлы отдельными чипами, авторские сообщения
с ProviderIcon. TaskFile и ссылки fileIds связывают сообщение с общей коллекцией.
В прототипе можно добавить txt/md/json/csv и png/jpeg/webp/gif до 5 МБ каждый;
предпросмотр в responsive Dialog. Данные живут в React, на сервер не передаются.
PDF и другие форматы не поддерживаются; постоянный backend/нативный FileLink
для сохранённого файла — следующий этап. Служебные запускающие кнопки по-прежнему
не вызывают агентов.
