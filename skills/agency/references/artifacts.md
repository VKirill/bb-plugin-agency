# Результаты: где лежат файлы, как сдать и принять

## Где что хранится

```text
<папка проекта на машине привязки>/
├── …файлы проекта            # код, тексты, данные — меняются там, где требует бриф
└── .agency/
    ├── jobs/
    │   └── AG-2203/           # рабочая папка поручения — пишет сотрудник
    │       ├── report.md      # обязательный отчёт исполнителя
    │       └── …              # логи проверок, скриншоты, выгрузки
    ├── originals/<artifactId>/v<N>   # неизменяемые копии опубликованных версий — пишет Агентство
    └── preview/…              # копии для просмотра в интерфейсе — пишет Агентство
```

- **Рабочие файлы** поручения — в `.agency/jobs/<ключ>/`, если бриф не называет другой путь. Изменения самого проекта (код, страницы, тексты) — в файлах проекта.
- **Опубликованная версия** — это регистрация файла в Агентстве: сервер копирует байты в `.agency/originals/…`, считает hash и привязывает версию к задаче. Правка файла после публикации — новая версия, старая не меняется.
- **Метаданные** MD/JSON-файла (принадлежность, источники) — по навыку `agency-artifacts`, если он доступен. Реестр версий остаётся в Агентстве, YAML его не заменяет.
- `.agency/` в git проекта обычно не нужна: предложи владельцу добавить её в `.gitignore`.

## Отчёт исполнителя

`.agency/jobs/<ключ>/report.md`:

```markdown
# Отчёт AG-N: <название>

## Итог
<1–3 предложения: сделано ли и что получилось>

## Что сделано
- <изменение> — <файл или место>

## Проверка
| Критерий приёмки | Результат | Как проверено |
| --- | --- | --- |
| <критерий из задачи> | пройдено / не пройдено / не проверено | <команда или место> |

## Не сделано и риски
- <что осталось, почему, что нужно>

## Для руководителя
<что посмотреть в первую очередь, следующий шаг>
```

Проверяющий пишет так же, но раздел «Что сделано» заменяет «Найденные дефекты»: критерий → место → как воспроизвести → серьёзность.

## Сдача работы

1. **Отчёт** — по шаблону выше.
2. **Регистрация артефакта** (один раз на файл):

   ```bash
   bb agency artifact create --input-json '{"requestId":"<uuid>","jobId":"<jobId>"}'
   ```

   Ответ содержит `artifactId`.
3. **Публикация версии.** `hash` — sha256 байтов файла (`shasum -a 256 <файл>`), `size` — размер в байтах, `relativePath` — путь от корня проекта.

   ```bash
   bb agency artifact publish --source server-fs --bytes-file <абсолютный путь> --input-json '{"requestId":"<uuid>","artifactId":"<artifactId>","jobId":"<jobId>","relativePath":".agency/jobs/AG-N/report.md","mime":"text/markdown","size":<байты>,"hash":"<sha256>"}'
   ```

   `--bytes-file` читает диск сервера BB. Сотрудник на другой машине передаёт содержимое в `bytesBase64` внутри `--input-json`.
4. **Явная сдача** для руководителя. Перечитай `job get`: нужна свежая ревизия задачи. Поля версии возьми из ответа публикации:

   ```bash
   bb agency job submit --input-json '{"requestId":"<uuid>","jobId":"<jobId>","expectedRevision":<ревизия задачи>,"artifactId":"<artifactId>","version":<N>,"hash":"<sha256>","comment":"Готово к проверке: <итог>. Отчёт: <artifactId> v<N>. Проверено: <кратко>. Не сделано: <или «нет»>."}'
   ```

5. **Завершить ход.** Агентство проверит опубликованные байты и явную сдачу, переведёт задачу в review и сообщит руководителю родительской задачи.

Сдача привязана к точным `artifactId/version/hash` текущей попытки. Новая публикация или возврат на доработку требуют новой сдачи. Прогресс и оценка на входе — обычные `job comment`, они не отправляют результат на приёмку. Родитель сдаётся после завершения рабочих детей и публикации итогового отчёта после их изменений.

`job state` показывает `handIn.protocol`. Новые запуски используют `explicit`; уже работавшие на момент обновления сохраняют `legacy` до первой явной сдачи. Это позволяет закончить текущую работу без перезапуска.

Завершил ход без версии или сдачи — придёт напоминание. После `completionReminders` напоминаний (по умолчанию 2) задача переходит в blocked и уходит руководителю.

Автор версии — попытка, из треда которой пришла публикация: сервер ставит `author: {kind: "run", runId}` сам. Из треда попытки публиковать можно только в задачу этой попытки (`artifact_foreign_job`). Материалы для подзадачи — `attach-input` или бриф.

## Проверка и приёмка

- Проверяют конкретную версию (`artifact versions`, `artifact open`), а не рабочую копию файла.
- Принять версию: `bb agency artifact accept` с `jobId`, `artifactId`, `version`, `hash`, `expectedRevision`. Устаревшую версию сервер отклонит.
- Публикация ≠ приёмка. approved в YAML не вызывает приёмку и не закрывает задачу.
- Кто принимает. Владелец — любую версию из интерфейса. Сотрудник из треда попытки — только версию подзадачи, которую поручила его задача (`parentJobId` = его задача). Результат своей задачи (`self_acceptance`), свою версию (`self_acceptance`) и чужую задачу (`accept_not_lead`) сервер не примет.
- Если интерфейса приёмки нет, передай заключение с версией и не объявляй задачу принятой.
