# Среда исполнения: где правда и как идёт запуск

## Источники истины

| Что | Где | Как читать |
| --- | --- | --- |
| Проекты, отделы, сотрудники, задачи, политики | База плагина | `bb agency workspace --json` |
| Карточка задачи с историей, версиями, вопросами | База плагина | `bb agency job get --input-json '{"jobId":"<id>"}'` или `{"key":"AG-12"}` |
| Отдел с регламентом и составом | База плагина | `bb agency department get --input-json '{"departmentId":"<id>"}'` |
| Сотрудник и текущая версия профиля | База плагина | `bb agency agent get --input-json '{"agentId":"<id>"}'` |
| Навыки и MCP для профиля | Каталог BB | `bb agency catalog capabilities --json` |
| Попытки запуска задачи | База плагина | `bb agency job attempts --input-json '{"jobId":"<id>"}'` |
| Файлы результата | Папка привязки на её машине | `bb agency artifact open` / `versions` — не произвольный путь |

PROJECT.md, YAML и заметки в репозитории — материалы проекта. Они не заменяют задачу, состав отдела, права или приёмку в базе. Если файл противоречит привязке (другая машина, другая папка), работу не переносят: фиксируют расхождение вопросом.

## CLI

- `bb agency` выполняется на машине сервера BB, а не на машине клиента чата.
- Payload передаётся только через `--input-json`. `--input-file` и `--bytes-file` читают диск сервера и требуют `--source server-fs`.
- Разрешены только операции из allowlist (`bb agency help`). Сырого RPC и SQL нет.
- Изменения идемпотентны по `requestId`: повтор с тем же `requestId` и тем же payload возвращает прежний результат, с другим payload — ошибку.
- `revision_conflict`: перечитай запись, пересобери изменение, не затирай чужое.
- Значения секретов и `bytesBase64` CLI не печатает. Не проси их вывести.

## Проекты и машины

- Привязка — одна папка на одной машине. Сотрудник запускается на этой машине (`environment: host + папка`) и работает с её файлами. Сервер BB только ставит задачи и хранит историю.
- Проект на нескольких машинах — несколько привязок (вторая папка одного BB-проекта подключается при установленном Projects & Sections). Работу в копии на другой машине ставят в её привязку; подзадача главной задачи может жить в другой папке того же проекта.
- Рабочее место сотрудника (при установленном File Gateway) — папка, где он работает всегда, например Mac mini с браузером. Задачи ему ставятся только туда; слой задачи называет папку главной задачи, её файлы сотрудник берёт входами или `bb file-gateway copy`.
- Плагины сотрудника — вкладка «Плагины» профиля. Их навыки и инструкции входят в снимок и промпт запуска; штатный BB 0.43 не передаёт отдельный allowlist инструментов в тред. Инструмента нет в сессии — пользуйся командой `bb <плагин>` из навыка плагина. Отмеченный плагин не установлен или выключен — `plugin_unavailable`.
- Песочница: правило «Запуск без песочницы» (Агентство → отдел → сотрудник), по умолчанию выключено. Включено — запуск с полными правами (`permissionMode: full`), в слое сотрудника об этом строка. В песочнице на Linux команды `bb` могут не доходить до сервера BB: не выходи из песочницы сам, закончи ход объяснением — без сданной версии Агентство после напоминаний переведёт задачу в blocked и сообщит руководителю. Команды, выполненные вне песочницы, карточка задачи показывает у попытки.
- Запуск на машине требует: хост онлайн в BB, CLI провайдера установлен и не выключен для машины в разделе «Машины», `.bb/AGENTS.md` в папке, политика разрешает `hostId`, машина есть в ролях навыков (`hostIds` в `agency-isolated-catalog-roles-v1`). `launch prepare` проверяет машину и CLI до снимка и возвращает причину: `host_offline`, `provider_disabled`, `provider_cli_missing`, `provider_cli_unsupported`, `catalog_host_mismatch`.
- Отключённая привязка (`archivedAt`) не принимает новые задачи, связи отделов и запуски. Идущие попытки не останавливаются.
- Правила проекта — `.bb/AGENTS.md` в папке привязки. Прочитать с любой машины: `bb agency project rules --input-json '{"bindingId":"<id>"}'`. Сохранить: `bb agency project rules-save` с `expectedHash` из чтения (null, если файла нет) — при `file_changed` перечитай и пересобери правку.

## Модели, которых нет в этом BB

Агентство можно перенести на другую машину или отдать другому человеку: у него подключены свои CLI и свои модели. Профиль сотрудника при запуске сверяется с каталогом машины проекта.

- Модель на месте — запуск идёт как обычно.
- Модели нет, но есть близкая — запуск не стартует молча на другой модели. `launch readiness` и `launch prepare` отвечают `model_unavailable` и называют замену.
- Стартовый набор и `repair-models` подставляют основную модель из каталога (Claude → GPT → Grok того же класса) и заполняют пустой список запасных из других подключённых семейств. Запас, который задал владелец и который всё ещё есть в каталоге, не переписывается. Только Claude в каталоге — запасных нет: называть нечего.
- Запасные модели сотрудника (`fallbackModels` в версии профиля, до 4 пар `providerId` + `model`, порядок = приоритет) задаёт владелец: вкладка «Исполнение» карточки или `bb agency agent save`. Пустой список при установке стартовых отделов и при «Перевести на доступные модели» заполняется сам. `launch prepare` идёт по списку «основная → запасная 1 → …» и стартует на первой паре, которая проходит готовность машины (CLI есть и разрешён, модель в каталоге) и которой BB не отказал в spawn. Дальше по списку — только при отказе именно этой пары: `provider_unavailable`, `provider_cli_missing`, `provider_cli_unsupported`, `provider_disabled`, `provider_constraint_mismatch`, `model_unavailable`, лимит/окно подписки. Машина не в сети, лимиты запусков, конфликт ревизии и неизвестный исход spawn список не листают. Профиль не переписывается; в истории задачи — строка «не запустилась на… запущена на…», в снимке `agentVersion.providerId/model` фактические и `modelSource: "fallback N"`. Ни одна пара не взялась — отказ перечисляет опробованные: `provider_unavailable`, если хоть один отказ преходящий (очередь ждёт), иначе `fallback_models_refused` (очередь снимает задачу с причиной).
- Лимит подписки у уже идущего треда: тред на другую модель не переключается. Попытка отменяется, пара помечается исчерпанной на 6 часов для этого сотрудника, задача уходит в очередь и стартует новой попыткой на следующей неисчерпанной паре. Исчерпанные пары встают в конец порядка; сохранение профиля сбрасывает пометки.
- «Ближайшая модель» каталога подставляет основную; `repair-models` ещё заполняет пустой список запасных из подключённых семейств. Запас, который задал владелец, не затирается, пока модель есть в каталоге. Запасная, ставшая основной, из списка уходит.
- `bb agency agent models --input-json '{}'` — все сотрудники против каталога: `exact`, `substituted` (есть замена) или `missing` (замены нет).
- `bb agency agent repair-models --input-json '{}'` — перевести сотрудников на доступные модели: у каждого появляется новая версия профиля с ближайшей моделью. То же делает кнопка «Перевести на доступные модели» в «Настройки → Машины → Модели сотрудников».
- Порядок подбора: та же модель под другим CLI → модель того же класса (сначала Claude, потом GPT, Grok, Gemini) → модель CLI по умолчанию. Быстрый режим при смене CLI не переносится.
- BB не отдал каталог моделей — ничего не блокируется: запуск идёт как раньше.

## Очередь запуска

Создание или назначение исполнителя (менеджер, правило автоматизации, следующий шаг, автопроверка) сразу ставит поручение в очередь запуска. Обход раз в 15 секунд вызывает `launch prepare`. Владелец не ставит задачу в очередь и не жмёт «Запустить». Если закреплена старая версия навыка (`catalog_skill_hash_mismatch`), задача остаётся в очереди: очередь сама закрепляет текущий пакет, когда это разрешено настройками. Снятую с очереди назначенную задачу без попытки очередь возвращает сама. Черновик без исполнителя остаётся в бэклоге.

## Запуск сотрудника

1. **Готовность:** `bb agency launch readiness --json`. Проверяет CLI сотрудника на машине проекта (`provider_unavailable`, если BB его там не знает или он не вошёл) и политики проекта и сотрудника: если они перечисляют CLI и не включают CLI сотрудника, причина говорит, где это открыть. Запускается любой CLI, подключённый в BB: Claude Code, Codex, Cursor, OpenCode, Antigravity. Запуск — скрытый тред `threads.spawn` (origin plugin).
2. **Подготовка:** `bb agency launch prepare --input-json '{"requestId":"<uuid>","jobId":"<id>","expectedRevision":<n>}'`. Собирается неизменяемый снимок контекста и создаётся скрытый тред. Ответ — квитанция с `launchId` и `attemptId`. Без квитанции запуск не объявляют.
3. **Сверка:** `launch get` читает квитанцию, `launch reconcile` сверяет тред и не перезапускает.
4. **Остановка:** `bb agency launch cancel` с `jobId`, `attemptId`, `launchId`, `threadId`, `expectedJobRevision`, `expectedAttemptRevision`, `reason`. Попытка отменяется, задача становится blocked и не отменяется.

У задачи одна активная попытка. Повторный запуск возможен после завершения или отмены предыдущей.

## Что получает запущенный сотрудник

Промпт запуска состоит из слоёв снимка, в этом порядке:

1. правила Агентства;
2. проект — привязка и правила проекта;
3. отдел — регламент и класс результата;
4. **должность** — роль, инструкция, модель, права, навыки;
5. поручение — бриф, критерий, входные версии;
6. передача от прошлой попытки, если была.

Нижний слой не отменяет верхний. Снимок фиксирует версии: правка регламента или профиля после запуска на идущую попытку не влияет.

Навыки доставляются в промпт запуска списком из профиля. Сотруднику Агентства нужен навык `agency`: в нём команды возврата, вопросов и публикации.

Раздел роли — «Your role: lead / executor / reviewer / assistant» с составом отдела и порядком работы — входит в слой поручения этого промпта. Следом идёт **базовая инструкция роли** владельца («Настройки → Шаблоны»): общий порядок работы для любого поручения, одинаковый для всех сотрудников этого типа роли. Её не нужно копировать в должностные инструкции.

Навыки сотрудника приходят в слой должности списком «название, id, хэш» с правилом: работа попадает под навык — прочитай его до начала и действуй по нему. Тела навыков в промпт не вставляются: в штатном BB 0.43 они не уезжают отдельным `skillIds` в тред, поэтому действуй по списку и читай файлы навыка, когда работа под него попадает. Инструкции плагинов в скрытый тред штатно не инжектятся (кроме текста в слое сотрудника), поэтому роль приходит с промптом. Системные тексты для агентов — на английском; строка «Language: …» в конце задаёт язык отчётов, комментариев и вопросов по настройке «Язык Агентства».

В обычных чатах BB Агентство добавляет инструкции треда. Режим места (проект / единственная папка / этот тред) перекрывает запасную настройку плагина «Инструкция делегирования в сессиях» (`delegate` / `suggest` / `off`):

- `pm` и запасной `delegate` — «BB Agency: you are the project manager»: чат — офис, работу не исполняет, сразу создаёт Job по [карте поступления](routing.md);
- `suggest` — «BB Agency: ask before handing work»: один вопрос — здесь или поручение;
- `ordinary` / `off` — инструкций нет, модель про Агентство не знает.

В интерфейсе три режима: «Агентство» (`pm`, заводской `delegate` даёт тот же текст), «По запросу» (`suggest`), «Сам сделает» (`ordinary`). Список в строке действий поля ввода, слева от MoA. В новом чате до отправки список ставит черновик только на этот следующий тред, а не на все чаты проекта. Треды сотрудников Агентства этот раздел не получают. CLI: `bb agency session get|save`.

## Сообщения руководителю

Когда подзадача переходит в review, waiting_input, blocked, done или canceled, Агентство отправляет в тред руководителя родительской задачи короткое сообщение с ключом и состоянием. Условия:

- тред руководителя ещё жив, попытка не завершена;
- подзадача этой задачи в любой папке; отдел может быть другим.

## Напоминание о сдаче

Если тред сотрудника завершил ход, задача всё ещё running, а опубликованной версии нет, Агентство через 20 секунд простоя пишет в тред напоминание с порядком сдачи. Следующее — только после нового хода сотрудника. После `completionReminders` напоминаний (по умолчанию 2) задача переходит в blocked с комментарием, руководитель получает сообщение. Руководителя, который ждёт свои открытые подзадачи, не напоминают.

## Наблюдение за попыткой

Раз в 5 секунд Агентство читает тред каждой идущей попытки. Признак работы — обновление треда, событие расхода токенов, запись в истории задачи или активный фоновый агент.

| Ситуация | Правило (по умолчанию) | Что происходит |
| --- | --- | --- |
| Тред активен без признаков работы | `watchQuietMinutes` (10 мин) | Системный комментарий в задаче |
| То же | `watchStallMinutes` (30 мин) | blocked с причиной «завис», сообщение руководителю |
| Тред не стартовал (pending / starting) | `watchStartMinutes` (10 мин) | blocked: проверить машину, CLI и авторизацию |
| Тред в ошибке (сбой провайдера, лимит подписки) | `watchErrorMinutes` (5 мин) | blocked |
| Тред активен без перерыва | `watchCeilingHours` (2 ч) | blocked: потолок одной попытки |

Пороги берутся из правил отдела задачи — см. «Правила работы».

Idle-тред не считается зависшим: его ведёт напоминание о сдаче. Наблюдение не останавливает тред: остановка — `bb agency launch cancel`, затем перезапуск или переназначение.

## Обходчик зависших задач

Периодический проход (раз в 5 мин) по задачам, которые стоят без движения. Это не наблюдение за живой попыткой (`watchStallMinutes`) и не вопрос за сырьём (`waiting_input` / `report-needs-input`).

**Когда срабатывает.** Состояние `blocked` или `running` без попытки, которую ведёт наблюдатель; нет открытой зависимости и задача не в очереди запуска; с последнего движения прошло больше порога. По умолчанию порог **1 час** (`staleHoursBlocked`, `staleHoursRunning`). Повтор — `staleRepeatHours` (24 ч), максимум `staleMaxAttempts` (3). `0` выключает порог или весь обходчик. `waiting_input` обходчик не берёт. Наблюдатель ведёт `active` / `pending` / `starting` / `error`. `running` + leftover-попытка с тредом `idle` — кандидат обходчика (как AG-106). Тихих часов нет.

**Что приходит в origin-чат.** Обычное сообщение агенту чата постановки (`originThreadId`), не карточка владельца: ключ, название, состояние, «с какого времени», последние комментарии, `nudgeId`, ревизия и готовая команда ответа. Несколько задач одного чата уходят одной пачкой. Явная инструкция: **не спрашивать владельца**, не вызывать `agency_ask_owner`. Доставили — адресат есть; иначе до 3 попыток и эскалация. Без `originThreadId` или при отказе отправки — только системный комментарий.

**Ответ** — из того же origin-чата:

```
bb agency job stale-answer --input-json '{
  "requestId":"<uuid>","jobId":"AG-73","nudgeId":"stale:…",
  "expectedJobRevision": 12,
  "decision":"close|cancel|keep|escalate",
  "reason":"…",
  "nextCheckHours": 24
}'
```

`expectedJobRevision` обязателен. `nextCheckHours` (1–168) — только при `keep`.

| decision | Исход |
| --- | --- |
| `close` / `cancel` без опубликованной версии | `canceled`, код **только** `closed_by_origin_agent` |
| `keep` | состояние то же, следующий опрос через `nextCheckHours` |
| `escalate` | одно сообщение во **Входящие** (`recordOwnerMessage`), не в Telegram; задача не закрывается |

После 3 попыток без ответа — та же эскалация во Входящие, задача остаётся. `done` обходчик не ставит.

**Отказы (состояние не меняется):** `needs_acceptance` — `close` при опубликованной версии; `revision_conflict` — устарела `expectedJobRevision`; `foreign_thread` — вызов не из origin-чата; `duplicate` — ответ на закрытый nudge.

## Правила работы

Настраиваемые пороги и политики. Три уровня: Агентство → отдел → сотрудник. Интерфейс: «Настройки → Правила работы», вкладка «Правила работы» в карточке отдела, лимиты во вкладке «Исполнение» профиля сотрудника.

| Ключ | По умолчанию | Уровни | Что делает |
| --- | --- | --- | --- |
| `reworkLimit` | 3 | Агентство, отдел | Лимит обычных возвратов. Дополнительно сервер останавливает повторы после третьего неудачного прохода, учитывая отмены и новые треды. Руководитель исправляет причину и разрешает одно продолжение через `job recover` с `recoveryDecision: {cause, correction, verification}`; общий бюджет не сбрасывается. |
| `minorDefectsWithoutRound` | false | Агентство, отдел | true — мелкие дефекты перечисляются в итоговом отчёте без нового круга |
| `watchQuietMinutes`, `watchStallMinutes`, `watchStartMinutes`, `watchErrorMinutes`, `watchCeilingHours` | 10, 30, 10, 5, 2 | Агентство, отдел | Наблюдение за попыткой |
| `staleHoursBlocked`, `staleHoursRunning`, `staleRepeatHours`, `staleMaxAttempts` | 1, 1, 24, 3 | Агентство, отдел | Обходчик зависших: спросить агента чата постановки. 0 выключает порог или весь обходчик. `waiting_input` и попытку под наблюдателем не трогает; idle-зомби берёт |
| `completionReminders` | 2 | Агентство, отдел | Напоминаний о несданной работе до blocked |
| `dueReminderHours` | 24 | Агентство, отдел | За сколько часов до срока напомнить |
| `budgetWarnPercent` | 80 | Агентство, отдел | Порог предупреждения о бюджете |
| `budgetMonthlyUsd`, `concurrencyLimit` | нет | Агентство, отдел, сотрудник | Лимит своего уровня; действует самый строгий |
| `defaultModel{Lead,Executor,Reviewer}`, `defaultReasoning{…}` | Opus 5 1M / Sonnet 5 / Opus 5 1M; high / medium / high | Агентство | Что подставляет форма «Создать сотрудника» |

### Лимиты запуска

`launch prepare` и `launch readiness` проверяют лимиты Агентства, отдела задачи и её исполнителя; срабатывает самый строгий:

- `concurrencyLimit` — сколько попыток уровня одновременно в состояниях prepared / launching / running. Сверх лимита — отказ `concurrency_limit_reached` с числами. Попытка самой задачи не считается. Две одновременные подготовки не проскочат лимит: проверка лимита и резерв попытки идут по очереди. По очереди идут только они — сбор снимка и `threads.spawn` чужой задачи ваш запуск не держат. `null` — лимита нет: у агентства, отдела и сотрудника может идти сколько угодно тредов, один сотрудник ведёт несколько задач сразу.
- `budgetMonthlyUsd` — оценка стоимости попыток, начатых в текущем календарном месяце (UTC), по ценам API. Весь тред считается в месяц запуска попытки. При 100% — отказ `budget_exhausted`; с `budgetWarnPercent` — запуск идёт, `warnings` в ответе и в панели запуска.
- Бюджеты и расход: `bb agency rules budgets --input-json '{}'`, в интерфейсе — «Дашборд → Бюджеты за месяц».

Отказ по лимиту — не ошибка сотрудника. Лимиты не обходи.

### Очередь запуска

Упёрся в лимит одновременных запусков, бюджет, незакрытую зависимость или пересечение файлов с работающей задачей (`launch readiness` вернул `waitable: true` с кодом `concurrency_limit_reached`, `budget_exhausted`, `dependencies_open` или `owns_overlap`) — поставь задачу в очередь:

```bash
bb agency launch queue --input-json '{"requestId":"<uuid>","jobId":"<jobId>","expectedRevision":<revision>}'
```

Задача из backlog переходит в queued. Раз в 15 секунд Агентство проверяет очередь: срочные первыми, затем по времени постановки; как только лимиты позволяют — запускает (`launch prepare` от системы) и пишет в историю «Запущена из очереди». Один обход запускает все годные задачи сразу, каждую в своём скрытом треде: вторая не ждёт, пока у первой поднимется тред. Задача, которую обход уже запускает, держит свой слот и свои файлы для следующих по очереди — при пересечении «Можно менять» или исчерпанном лимите слот достаётся более приоритетной, остальные ждут с причиной. Пока ждёт — в карточке позиция и причина.

Временный отказ (машина не в сети, провайдер недоступен, 5xx, таймаут) очередь не считает окончательным: задача остаётся в очереди, попытки продолжаются, через 10 минут владелец получает сообщение во «Входящие», и только через час задача снимается. Ожидание (`catalog_skill_hash_mismatch`, лимиты, зависимости) задачу не снимает. Окончательный отказ (правила проекта, права) снимает задачу сразу — с комментарием в истории и сообщением владельцу. Назначенная задача без попытки, которую очередь уже снимала, возвращается в строй на следующем обходе. Задача в состоянии queued, потерявшая запись очереди и без попыток, возвращается через 5 минут. Убрать: `bb agency launch unqueue --input-json '{"jobId":"<jobId>"}'`. Сообщение о старте подзадачи придёт руководителю как обычно.

### Сроки

`dueAt` задачи. Раз в минуту Агентство проверяет открытые задачи со сроком: за `dueReminderHours` до срока — комментарий «Срок …: осталось N ч» и сообщение в тред работающего сотрудника; после срока — комментарий «прошёл» и сообщение. По одному разу на каждый срок; новый срок — новые напоминания. На доске срок подсвечивается: жёлтый — скоро, красный — просрочен.

Получил напоминание о сроке и не успеваешь — сразу комментарий руководителю: причина и новая оценка. Готовое сдавай версией, не жди срока.

«Проверка обязательна» — не правило, а процесс отдела (`process.reviewPolicy.required` в `department save`); руководитель получает её в инструкции.

- Прочитать: `bb agency rules get --input-json '{"scope":"agency"}'` (или `department:<id>`, `agent:<id>`). Ответ: `stored` — заданное на уровне, `effective` — по чему работает уровень, `sources` — откуда значение.
- Сохранить: `bb agency rules save --input-json '{"requestId":"<uuid>","scope":"department:<id>","expectedRevision":<revision из get>,"rules":{"reworkLimit":2}}'`. `rules` — полный набор уровня: отсутствующий ключ возвращается к унаследованному значению. Ключ чужого уровня — `rule_not_in_scope`.
- Меняет правила только владелец или по его прямой просьбе.

## Общие правила и шаблоны

- **Общие правила Агентства** — верхний слой промпта каждого запуска (слой agency, над правилами проекта). Владелец пишет их в «Настройки → Общие правила»; каждое сохранение — новая версия. Снимок запуска закрепляет версию (`agencyRules.versionId`); если правила изменились после `launch prepare`, запуск отклоняется (`live_agency_rules_mismatch`) — подготовь заново. CLI: `bb agency rules agency-get --input-json '{}'`, `bb agency rules agency-save --input-json '{"expectedVersion":<latestVersion>,"text":"…"}'` — только по прямой просьбе владельца; пустой текст выключает слой.
- **Шаблоны форм** — регламент отдела, должностные инструкции руководителя, исполнителя и проверяющего, бриф и критерии приёмки. С них начинаются формы интерфейса; существующие записи не меняются. CLI: `bb agency templates list --input-json '{}'`, `bb agency templates save --input-json '{"key":"brief","expectedRevision":<revision>,"text":"…"}'` (`text: null` — вернуть стандартный). Создавая отдел или сотрудника через CLI, бери текст из `templates list`, а не из памяти.
- **Версии навыков** — «Настройки → Машины → Навыки Агентства»: закреплённый хэш против текущего пакета. Расхождение (`catalog_skill_hash_mismatch`) оставляет задачу в очереди; сервер сам закрепляет текущий пакет, если закрепление правится из настроек. Из треда сотрудника не закрепляй.

## Знания, цели, эскалация

Ниже — устройство: что где хранится и как доходит до запуска. Что именно записывать, какими
словами и когда — [Память](memory.md).

- **Знания** — материалы с областью: Агентство, отдел или проект (привязка). У записи есть **сводка** (одна строка), **тело**, **вид** (`fact`, `decision`, `procedure`, `preference`, `reference`, `lesson`), **важность** 0–100 и **закрепление**. В запуск приходит **индекс сводок** всех принятых записей своей области; целиком — только закреплённые и важные (от 80), до 8 000 знаков на слой. Полный текст любой записи: `bb agency knowledge get --input-json '{"id":"kno_…"}'`.
- **Уроки** — после приёмки главной задачи Агентство само складывает в знания отдела черновик: сколько было подзадач и кругов доработки, из-за каких замечаний возвращали, сколько заняло. При правиле «Отдел учится сам» (`autoLearn`, включено по умолчанию) урок принимается сразу, а владелец получает сообщение и может поправить его или убрать; при выключенном правиле урок ждёт решения владельца предложением. Один урок на задачу. Память отдела держится в рамках: сверх `memoryLimit` записей в архив уходят сначала те, которые никто ни разу не открывал, потом наименее важные и старые, авто-урок старше `memoryTtlDays` архивируется ночной уборкой — закреплённые записи не вытесняются и не устаревают. Принять или убрать урок, процедуру или справку своего отдела может и его руководитель: `bb agency knowledge status --input-json '{"id":"<kn_…>","expectedRevision":<n>,"status":"archived"}'`; знания проекта и всего Агентства решает владелец. Это справка, не приказ: противоречие с регламентом или поручением — вопрос руководителю. Сотрудник может предложить материал: `bb agency knowledge save --input-json '{"expectedRevision":0,"title":"…","body":"…","source":"откуда факт","scopeKind":"department","scopeId":"<dep_…>"}'` — из треда попытки он сохранится как предложение и попадёт в запуски только после принятия владельцем.
- **Индекс знаний в промпте** — принятые записи области приходят строками «вид, название, сводка, id», не длиннее 3500 знаков на уровень; что не поместилось, объявлено строкой «Показано N из M» и берётся командой `bb agency knowledge list`. Наверх идут закреплённые и важные, затем те, к которым возвращаются: каждое чтение через `bb agency knowledge get` учитывается. Название записи в области одно: повтор — это правка существующей, а не вторая запись рядом.
- **Библиотека навыков отдела** — навыки, которые отдел вправе поднять под конкретное задание, даже если их нет в профиле сотрудника. Оценщик открывает оттуда не больше двух и только если без навыка результат заметно хуже (чтобы работа была качественнее), на один запуск; каждая выдача попадает в журнал. Смотреть и править: `bb agency skills pool|pool-save|grants` — владелец или руководитель этого отдела. `pool-save` по умолчанию заменяет список; `"mode":"merge"` дописывает, не затирая. Пусто — работают только профили, и оценщику нечего открыть.
- **Подсказка к запуску** (точка оценщика `launch-briefing`) — перед стартом задачи Агентство спрашивает оценщика, какие из **методических** навыков сотрудника (не core/helper `agency`) нужны этой работе, что открыть из библиотеки отдела и какие записи памяти отнести к делу, и кладёт в уровень задачи короткую строку. У исполнителя и помощника отдельный запрос по полному заданию (название, бриф, приёмка, контракт), без обрезания, служебных инструкций, навыков и памяти выбирает reasoning из реального каталога выбранной модели, включая `xhigh` / `max`, когда поддерживаются. Решение явно передаётся в `threads.spawn.reasoningLevel` только для этой попытки. Профиль не переписывается; ошибка, отсутствие каталога или уверенность ниже 60% оставляют уровень профиля. Журнал `launch-effort` фиксирует причину, итоговый уровень, hash и длину плана. `bb agency decisions probe --input-json '{}' --json` отдельно проверяет длинный план через живой Jev без запуска сотрудника. Это подсказка, а не приказ: бриф и регламент выше. Если у сотрудника в профиле только `agency`, библиотека отдела пуста и роль не писатель/помощник, спрашивать нечего — в журнале будет `empty`. Молчание после вопроса — `silent` с ответами. Если оценщик на длинном списке (от четырёх) выбрал больше половины, подсказки по навыкам в промпте нет: это снова весь список.
- **Оценщик** (необязателен, включает владелец) — быстрая модель, которая отвечает типизированным решением, а не текстом. Её спрашивают в точках, где правило грубое: привратник памяти (перед записью урока), оценка на входе (`intake` — комментарий с размером, риском и решением; подзадачи не создаёт), привратник сдачи (`hand-in-gate` — уверенный мусор возвращает исполнителю, принятие не пропускает независимую проверку), подсказка к запуску и привратник паспорта. Ответ ниже порога уверенности не применяется, а ошибка и таймаут равны «не знаю»: Агентство работает по своим правилам. Подключений два вида: модель решений (`openrouter-decisions`, `typesafe` — вопросы уходят картой на отдельный эндпоинт) и обычная модель через чат с JSON-схемой. Настройки и проверка: `bb agency decisions get|save|test|log|probe`; ключ берётся по имени из плагина Env Catalog или из окружения машины и в базе Агентства не хранится. Каждое обращение пишется в журнал (`decisions log`): точка, задача, исход, ответы с уверенностью и время. Молчание тоже видно.
- **Паспорт проекта** — сводка «что это за проект» на пять разделов: что это, кто пользуется, устоявшиеся решения, чего здесь не делают, куда идём. Приходит в слой проекта рядом с правилами проекта. Сколько его доходит до сотрудника, решают правила работы `passportForLead|ForExecutor|ForReviewer|ForAssistant` (по умолчанию: руководитель и проверяющий — целиком, исполнитель — шапка, помощник — строка с командой), личное правило сотрудника `passportDelivery` сильнее. Собирает паспорт фоновая модель («Настройки → Оценщик → Писарь паспорта») из знаний проекта, профилей работ, целей и принятых результатов — через `triggerEveryN` принятых задач; редакция применяется сразу, прежняя остаётся в истории. Перед заменой её смотрит точка оценщика `passport-gate`, если она включена в настройках оценщика: секрет или состояние дня отменяют замену, владелец получает сообщение; выключенная точка означает, что редакция применяется без проверки. Снимок запуска закрепляет `passportHash` — видно, какую редакцию читал сотрудник. Правка или откат владельца держатся вдвое дольше обычной редакции (двойной порог принятых задач): он правил паспорт не для того, чтобы модель молча вернула своё. Материал сборки уходит во внешнюю модель, поэтому в настройках есть свой адрес — для закрытого проекта укажите его или не включайте писаря. Паспорт и профили работ читаются только в своём проекте: тред чужого проекта получает `forbidden`. CLI: `bb agency passport show|build|save|rollback`, настройки — `passport settings|settings-save`.
- **Цели** — над главными задачами: `bb agency goal list`, привязать главную задачу: `bb agency goal link --input-json '{"jobId":"<job_…>","goalId":"<gol_…>"}'`. Подзадачи относятся к цели через главную.
- **Подчинённость и эскалация.** Отдел может подчиняться другому. Главная задача отдела в «Ожидает решения» дольше `escalateAfterHours` (правило работы, по умолчанию 24 ч) эскалируется в вышестоящий отдел один раз: комментарий в истории и пометка на доске.
- **Поиск и архив.** Закрытое дерево задач старше срока настройки «Убирать закрытые задачи в архив» уходит из рабочей доски, но остаётся в базе: `bb agency job search --input-json '{"query":"…"}'` ищет по ключу, названию, брифу и комментариям с архивом в проектах, доступных вызывающему, `bb agency job archive` — список архива. Владелец видит то же на доске «Задачи»: кнопка «Архив», блок «Ещё найдено» под списком и сохранённые виды фильтров. Карточка архивной задачи открывается только для чтения.
- **Показатели сотрудника:** `bb agency agent metrics --input-json '{"agentId":"<agt_…>"}'` — загрузка, закрытые за 30 дней, доля без возвратов на доработку, медианный срок, расход за 30 дней.

## Резервные копии

«Настройки → Хранение»: копия базы Агентства (согласованный снимок SQLite с учётом WAL) и восстановление. Перед восстановлением автоматически сохраняется копия текущего состояния. Секреты webhook и закрепление навыков хранятся вне базы и не входят в копию. Восстанавливает только владелец.

## Расход и стоимость

- Токены собираются из событий `thread/tokenUsage/updated` тредов попыток. Считаются `claude-code` и `codex`: у обоих один и тот же вид событий — накопительный итог сессии со сбросами. ACP-провайдеры (Cursor, OpenCode, Antigravity) событий расхода не присылают вовсе, их треды остаются «неизвестно».
- Расход подписок — `bb agency usage providers`: план, окна, процент и время сброса по данным BB. Для CLI без токенов это единственный источник; `countsTokens` в ответе говорит, считает ли Агентство токены этого CLI.
- Модель без цены попадает в расход по токенам, но не в деньги. Дашборд называет такие модели строкой в «Как это посчитано».
- Карточка главной задачи показывает сумму по ней и всем подзадачам: токены и оценку стоимости. Подробно — «Дашборд» с фильтрами по проекту, отделу, модели и задаче.
- Стоимость — оценка по ценам API, USD: входные без кеша, чтение кеша, ответы. Запись в кеш в событиях не приходит, поэтому оценка — нижняя граница. На подписке это эквивалент, а не счёт.
- Цены задаются таблицей: «Настройки → Цены моделей» — модель, вход, кэш, ответ в USD за миллион токенов. Модели, на которых работают сотрудники, стоят первыми и добавляются одной кнопкой. Цены Claude встроены (проверены 2026-09-16 по platform.claude.com/docs/en/about-claude/pricing), их можно изменить и вернуть обратно; в настройке плагина хранятся только отличия от встроенных. Модель без цены показывается как «Нет цены».
- CLI: `bb agency job usage --input-json '{"rootJobId":"<jobId>"}'` — `totals` (токены), `costUsdCents` (оценка в центах), `cost` (сколько тредов с ценой, модели без цены), `rows` по попыткам. Без `rootJobId` — весь расход, фильтры `departmentId`, `model`, `fromDate`, `toDate`.

## Доска

Закрытые задачи уходят с доски: подзадачи через 1 ч, остальные через 24 ч (настройки плагина). В базе и истории они остаются, карточка главной задачи показывает все подзадачи.

## Чего нет

- Файловой песочницы сотрудника: запуск получает только навыки и плагины профиля, но файлы изолирует песочница CLI, а не Агентство.
- Доставки MCP из профиля сотрудника в запуск: инструменты приходят только из отмеченных плагинов BB.
- Приёмки по тексту «готово» и waiting_input по тексту треда: только typed-команды.
- Копирования версии-входа больше 6 МБ между машинами: такой файл переносят через File Gateway.

## Служебный контекст сотрудников (VK)

На VK-сборке BB владелец задаёт фильтры в «Сотрудник → Навыки» и «Отдел → Библиотека навыков».
Команды: `bb agency context get|save --input-json`. Вход чтения: `scope: agent|department`, `scopeId`.
Сохранение добавляет `requestId`, свежий `expectedRevision` (0 для новой записи) и `policy`.
Поля `skills`, `bbPlugins`: `{mode: assigned|allow|deny, names: string[]}`; `mcpServers`, `nativePlugins`: только allow/deny.
`assigned` оставляет назначенное профилем и задачей плюс перечисленные имена; allow — только список, deny — всё кроме списка.
Имена — из каталога, не skill_ID; у native MCP — из конфигурации провайдера. Поля-флаги: `userInstructions`, `projectInstructions`, `claudeAiSync`.

Отдел задаёт значения по умолчанию, сотрудник переопределяет отдельные поля. `{}` возвращает наследование.
Настройки фиксируются в снимке нового запуска. Идущая сессия не меняется; повторное использование reviewer с другой политикой не выполняется.
Обязательные служебные навыки и Агентство остаются. Политика заменяет project-folders в этом служебном треде; обычные чаты не затрагиваются.
Это фильтр загружаемого контекста, не выдача прав и не песочница. Без экспериментального API настройки недоступны.
