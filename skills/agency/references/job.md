# Поручения: от чата до приёмки

## Состояния

```text
backlog → queued → running → review → done
                     ↓
          waiting_input / blocked / canceled
```

| Состояние | Смысл | Кто двигает дальше |
| --- | --- | --- |
| backlog | Создано, не передано в работу | Руководитель или владелец: назначить и запустить |
| queued | Готово к запуску: есть исполнитель, привязка, бриф, критерий | Запуск (`launch prepare`) |
| running | Идёт попытка в треде | Watcher: `idle` + hash-проверенная версия → review. `idle` без такой версии оставляет running |
| waiting_input | Исполнитель задал вопрос через `report-needs-input` | Ответ `answer-needs-input` в тот же тред |
| blocked | Работа стоит: возврат, блокер, остановленная попытка | Руководитель или владелец |
| review | Опубликована версия, ждёт проверки | Приёмка версии → done; доработка → running с комментарием |
| done | Текущая версия принята | — |
| canceled | Отменено, конечное | — |

Переходы проверяет сервер. queued и running требуют исполнителя, привязку, бриф и критерий. Переход review → done требует принятую текущую версию. Waiting_input никогда не выставляется по тексту треда. Watcher тоже его не ставит, только typed `report-needs-input`.

Вручную задачу переводят только: backlog → queued / canceled, queued → canceled, blocked → queued / canceled, review → canceled. running, review, done и waiting_input ставит сама работа: запуск, сдача версии, приёмка, вопрос.

**Возврат на доработку** — не `job transition`, а отдельная команда: замечания уходят в тред исполнителя, задача снова running, на проверку она вернётся только с новой версией (другой hash):

```bash
bb agency job return --input-json '{"requestId":"<uuid>","jobId":"<id>","expectedRevision":<revision>,"comment":"Что исправить: …"}'
```

**Запреты сервера** (ошибка вместо «попробую»):
- `agent_inactive` — приостановленному сотруднику нельзя назначить задачу и нельзя его запустить;
- `job_has_live_run` — пока тред попытки может работать, нельзя сменить исполнителя или отдел и нельзя отменить задачу: сначала `launch cancel`;
- `assignee_is_reviewer` — исполнитель не может быть проверяющим своей задачи;
- `self_review` — проверяющему нельзя дать на проверку его собственную работу;
- `member_has_open_jobs` — нельзя убрать из отдела сотрудника с открытыми задачами в нём;
- `duplicate_department_name` — названия отделов не повторяются.

Руководитель родительской задачи получает сообщение в свой тред, когда подзадача (своего или другого отдела, в любой папке) переходит в review, waiting_input, blocked, done или canceled. Опрашивать статус циклом не нужно.

Сервер переводит running в blocked сам, с системным комментарием о причине: два напоминания о несданной версии, тред завис без событий, не запустился, застрял в ошибке или упёрся в потолок попытки. Подробно — [Среда исполнения](runtime.md).

## Поручить из чата (диспетчер)

1. **Маршрут.** Мелкое, срочное, вопрос, настройка BB — сделай сам. Многошаговое, с отдельным результатом, нужна проверка, переживёт чат — поручи. Не уверен — одной фразой предложи владельцу.
2. **Отдел.** Сверь суть результата с разделом «Принимаем» отделов. Агентство добавляет их список в инструкции чата; полный текст — `bb agency workspace --json` (`processVersions`). Подходящего нет — не создавай, скажи, какого отдела не хватает.
   **Проект.** Выбери привязку, где лежит папка твоего окружения (сравни `pwd` с `canonicalRoot`): сотрудник запустится на её машине. Проект не подключён или отключён — поручение не создавай, скажи владельцу подключить папку в разделе «Проекты».
3. **Бриф.** По шаблону из [Должностные инструкции](job-descriptions.md), раздел 5. Критерий приёмки должен проверяться без автора.
4. **Создай на руководителя отдела:**

   ```bash
   bb agency job create --input-json '{"requestId":"<uuid>","bindingId":"<bindingId>","departmentId":"<departmentId>","assignedAgentId":"<leadAgentId>","title":"…","brief":"…","acceptance":"…"}'
   ```

   `key` назначит сервер. Необязательно: `priority` (low / normal / high / urgent), `dueAt` (ISO UTC), `parentJobId`.
5. **Запуск,** если владелец просит начать сразу: `bb agency launch readiness`, затем `bb agency launch prepare --input-json '{"requestId":"<uuid>","jobId":"<id>","expectedRevision":<revision>}'`. Нет готовности — оставь в backlog и скажи почему.
6. **Сообщи владельцу:** ключ AG-N, отдел, руководитель, запущено или ждёт запуска. Поручённую работу сам не делай.

## Цикл руководителя

Тред запущен на задачу, где ты исполнитель и руководитель отдела.

1. **Оценка на входе — первым действием.** Сверь поручение с регламентом отдела и запиши оценку данными: комментарий с обоснованием (профиль, входы) и тремя references — размер, риск, решение. Оценка показывается в карточке задачи; у запущенной главной задачи без оценки карточка пишет «Оценки на входе нет».

   ```bash
   bb agency job comment --input-json '{"requestId":"<uuid>","jobId":"<id>","comment":"Оценка: наш профиль, входы есть. Две подзадачи: реализация и проверка.","references":[{"type":"intake_size","id":"M"},{"type":"intake_risk","id":"medium"},{"type":"intake_decision","id":"split"}]}'
   ```

   Значения: `intake_size` S / M / L; `intake_risk` low / medium / high; `intake_decision` accept (беру целиком) / split (разбиваю на подзадачи) / clarify (нужен ответ владельца) / return (не наш профиль). Все три — ровно по одному, иначе сервер отклонит комментарий.
   - Не наш профиль — возврат владельцу (раздел «Возврат»).
   - Не хватает входов или решение за владельцем — `report-needs-input`.
   - Размер L — предложи владельцу этапы, не раздувай одну задачу.
2. **Декомпозиция.** Подзадачи с одним результатом и одним исполнителем:

   ```bash
   bb agency job create --input-json '{"requestId":"<uuid>","bindingId":"<папка подзадачи>","departmentId":"<отдел>","parentJobId":"<id главной задачи>","assignedAgentId":"<участник по роли>","title":"…","brief":"…","acceptance":"…"}'
   ```

   Работа другого отдела — подзадача в том отделе на его руководителя. Сообщения о ней приходят так же, как о подзадачах своего отдела.

   **Папка подзадачи** (`bindingId`) — по умолчанию папка главной задачи. Другая папка нужна в двух случаях, их перечисляет слой задачи в промпте:
   - «Other folders of this project» — работа идёт в копии проекта на другой машине (плагин Projects & Sections): передай `bindingId` той папки.
   - «Employees … with their own workplace» — у сотрудника рабочее место на своей машине (плагин File Gateway): его подзадача ставится только в папку рабочего места, иначе `workplace_binding_required`.
   Чужой проект — `binding_mismatch`; без нужного плагина — `integration_required`. Проверку рядом с такой работой и зависимости внутри одного дерева задач сервер разрешает сам. Версию-вход из другой папки `attach-input` копирует в папку подзадачи со сверкой хэша (до 6 МБ; больше — через File Gateway).

   **Автоназначение.** Не знаешь, кто свободен, — вместо `assignedAgentId` передай `"assignment": "executor"` или `"reviewer"`: сервер выберет активного сотрудника этого типа на запускаемом CLI с наименьшим числом открытых задач (`"lead"` — руководитель отдела). Нет подходящего — `no_member_for_assignment`.

   **Контракт исполнения** — граница работы для подзадачи реализации, поле `contract`:

   ```json
   "contract": {"mayChange": ["src/cards/**"], "mustNotTouch": ["src/billing/**", "публичный API"], "checks": ["npm test", "npm run build"]}
   ```

   Контракт попадает в промпт запуска и закрепляется в снимке: правка после `launch prepare` делает подготовленный запуск недействительным (`live_job_mismatch`). Изменить — `job update` с новым `contract`, очистить — `"contract": null`.
3. **Входы.** Результат одной подзадачи для другой передай версией: `bb agency job attach-input` (`targetJobId`, `sourceJobId`, `artifactId`, `version`, `hash`). Ссылка на родителя не даёт доступа к файлам.
4. **Порядок подзадач.** Подзадача, которой нужен результат другой, ждёт её: `bb agency job depend --input-json '{"requestId":"<UUID>","jobId":"<ждёт>","dependsOnJobId":"<должна быть готова>"}'`. Пока зависимость не готова, запуск отвечает `dependencies_open`; поставь такие подзадачи в очередь (`bb agency launch queue`) — каждая стартует сама, когда её зависимости будут готовы. Отменённая зависимость снимает задачу с очереди (`dependency_canceled`): реши сам. Убрать — `job undepend`. Циклы сервер не пускает (`dependency_cycle`).
   **Следующий шаг** — работа другого отдела после приёмки: `bb agency job next-step --input-json '{"jobId":"<ранняя задача>","step":{"departmentId":"…","title":"…","brief":"…","acceptance":"…","assignment":"lead"}}'`. Когда ранняя задача станет done, Агентство само создаст задачу рядом с ней (та же папка, тот же родитель), приложит принятые версии и поставит в очередь; итог пишется в историю обеих задач. `step: null` убирает шаг; выполненный шаг не меняется.
5. **Запуск подзадач:** `launch readiness` → `launch prepare`. Реализацию назначай участникам `executor`, проверку — `reviewer`. Проверяющему нельзя передать на проверку его собственную работу: `attach-input` и переназначение вернут `self_review`. Его прежнее заключение как контекст повторной проверки передавать можно.
6. **Реакция на сообщения Агентства:**
   - review — прочитай итоговый комментарий и отчёт (`job get`: activity и artifacts), проверь по критерию сам или назначь подзадачу проверки;
   - blocked с «Возврат» — переназначь (`job update` с `assignedAgentId`), перенеси в подходящий отдел или отмени; живую попытку останови `bb agency launch cancel`;
   - waiting_input — вопрос у владельца, не дублируй;
   - done / canceled — сверь открытые подзадачи.
7. **Дефекты.** Подзадача доработки с перечнем дефектов, затем повторная проверка. Три круга без результата — вопрос владельцу.
8. **Итог.** Сверь каждую подзадачу. Принимай (`artifact accept`) только версии подзадач, которые поручил сам. Устаревшую версию, заменённую новой, не оставляй в review: отметь замену и отмени устаревшую задачу. Опубликуй сводный отчёт версией главной задачи. Свой итог не принимай.

## Цикл исполнителя

1. **Прочитай слои промпта:** регламент отдела, свою должностную инструкцию, поручение и входные версии (`bb agency job get`).
2. **Сверь с пулом работ до начала.** Не твоё, не хватает входов — возврат. Частично твоё — делай свою часть, остальное перечисли руководителю комментарием.
3. **Работай в границах брифа и контракта.** Не трогай файлы и проекты вне поручения. Есть контракт исполнения — «Нельзя трогать» не меняй, все «Проверки перед сдачей» пройди и перечисли в итоговом комментарии; выйти за границу — вопрос руководителю, не решение. Существенные этапы — короткие комментарии `job comment`: что сделано, чем проверено, что дальше. Не по комментарию на каждое действие.
4. **Самопроверка** по должностной инструкции и критерию приёмки.
5. **Сдача:** отчёт `.agency/jobs/<ключ>/report.md` → `artifact create` и `artifact publish` → итоговый `job comment` для руководителя → завершить ход. Подробно и шаблон отчёта — [Результаты](artifacts.md). Задача перейдёт в review, когда тред станет idle, версия подтвердится hash и есть итоговый комментарий; руководитель получит сообщение.
6. **Не принимай свой результат,** не переводи задачу в done — сервер не даст (`self_acceptance`). Завершил ход без версии или без комментария — придёт напоминание, после лимита задача уйдёт руководителю в blocked.

## Возврат: задача не по профилю

Работа, начатая «на всякий случай», хуже возврата: она тратит бюджет и путает проверку.

**Когда возвращать:**
- поручение из «Не мой пул» должностной инструкции или «Не принимаем» регламента;
- нет обязательного входа из инструкции;
- для выполнения нужна чужая роль (исполнитель получил проверку собственной работы и наоборот).

**Как вернуть:**

1. Комментарий, который руководитель поймёт без переписки:

   ```bash
   bb agency job comment --input-json '{"requestId":"<uuid>","jobId":"<id>","comment":"Возврат: <почему не мой пул — ссылка на пункт инструкции>. Подходит: <роль или отдел>. Чтобы взять, нужно: <что изменить или добавить>."}'
   ```

2. Задачу в blocked (`expectedRevision` — текущая revision из `job get`):

   ```bash
   bb agency job transition --input-json '{"requestId":"<uuid>","expectedRevision":<revision>,"jobId":"<id>","to":"blocked"}'
   ```

3. Заверши ход коротким сообщением «Возвращено руководителю: <причина>». Работу не начинай.

**Кто получает возврат:**
- возврат подзадачи получает руководитель родительской задачи сообщением Агентства;
- главную задачу видит владелец в «Требуют внимания».

Руководитель, получивший главную задачу не по профилю отдела, возвращает её так же и предлагает подходящий отдел.

**Не путать:**
- вопрос по содержанию (что выбрать, какой вариант) — `report-needs-input`, а не возврат;
- противоречие регламента и брифа — тоже вопрос, а не возврат.

## Формат комментария

История задачи показывает комментарии Markdown и сворачивает длинные. Пиши так, чтобы первая строка читалась без раскрытия:

- **Первая строка — итог:** «AG-5 сдана: D1–D3 исправлены, тесты 17/17».
- **Детали — список Markdown.** Переносы в JSON — `\n`: `"comment":"AG-5 сдана: …\n\n- D1 …\n- D2 …"`.
- Ключи задач и версии — только те, что нужны читателю; технические id (`run_…`, `thr_…`, `job_…`) — не в текст, а в `references`, если нужны.
- Больше ~8 строк — это отчёт, а не комментарий: опубликуй версией и дай ссылку.

## Вопрос владельцу

`bb agency job report-needs-input` с `jobId`, `attemptId`, `launchId`, `threadId`, `expectedRevision`, `expectedAttemptRevision` и вопросами, у каждого `sourceRefs`. Задача и попытка переходят в waiting_input. После успеха заверши ход сообщением с `waitId`. Продолжение придёт отдельным сообщением в этот же тред. Не вызывай AskUserQuestion и не держи ход открытым.

Новый вопрос после ответа — новый `report-needs-input` с новым `waitId`.

## Два критерия приёмки

Сопоставь результат с Job.acceptance и регламентом (ProcessVersion.acceptance). Если оба нельзя выполнить одновременно, процитируй оба источника (processVersion id и job id) и остановись как needs clarification через `report-needs-input`: не auto-pick одного текста, не success, не accept.

## Проверка

1. Открой проверяемую версию с hash (`artifact open` / `artifact versions`), не рабочую копию файла.
2. По каждому критерию: пройдено / не пройдено / не проверено — с командой или местом.
3. Дефект: критерий → место → как воспроизвести → серьёзность.
4. Опубликуй заключение версией своей задачи. Решение о приёмке — у руководителя или владельца.

Принять версию: `bb agency artifact accept` (`jobId`, `artifactId`, `version`, `hash`, `expectedRevision`) — только тот, кому это разрешено процессом, и только текущую версию. После приёмки и выполнения политики ревью задачу переводят в done.
