# Поручения: от чата до приёмки

## Состояния

```text
backlog → queued → running → review → done
                     ↓
          waiting_input / blocked / canceled
```

| Состояние | Смысл | Кто двигает дальше |
| --- | --- | --- |
| backlog | Создано, не передано в работу | Руководитель или владелец: назначить и запустить |
| queued | Готово к запуску: есть исполнитель, привязка, бриф, критерий | Запуск (`launch prepare`) |
| running | Идёт попытка в треде | Watcher: `idle` + hash-проверенная версия → review. `idle` без такой версии оставляет running |
| waiting_input | Исполнитель задал вопрос через `report-needs-input` | В чате заказчика (`originThreadId`) открывается штатная карточка выбора; ответ `answer-needs-input` будит рабочий тред |
| blocked | Работа стоит: возврат, блокер, остановленная попытка | Руководитель или владелец |
| review | Опубликована версия, ждёт ОТК или автозакрытия | Конвейер принимает текущую версию → done; `Вердикт: доработать` → running с комментарием. Владелец не штампует станцию. |
| done | Текущая версия принята | Корень: «Продукт готов» уходит в чат заказчика (`originThreadId`). Можно вернуть продукт целиком (`job return`, рекламация) → running в том же треде. Закрытую подзадачу по одной не возвращают. |
| canceled | Отменено, конечное | — |

Переходы проверяет сервер. queued и running требуют исполнителя, привязку, бриф и критерий. Переход review → done требует принятую текущую версию; `artifact accept` в review сразу ставит done. Waiting_input никогда не выставляется по тексту треда. Watcher тоже его не ставит, только typed `report-needs-input`. Владельца зовут только в waiting_input (нет сырья: секреты, деньги, необратимое). Станции ОТК и Accept не ждут человека. Задача с открытыми рабочими подзадачами остаётся в review. После завершения работ руководитель публикует свежий итоговый отчёт по исходным критериям; старый промежуточный отчёт корень не закрывает. Зависшая проверка не означает приёмку: через 30 минут ожидания запуска она передаётся руководителю в blocked, работа остаётся непроверенной. Во «Входящих» владельца только waiting_input и blocked у корня; blocked у подзадачи разбирает руководитель.

Вручную задачу переводят только: backlog → queued / canceled, queued → canceled, blocked → queued / canceled, review → canceled. running, review, done и waiting_input ставит сама работа: запуск, сдача версии, приёмка, вопрос.

**Возврат на доработку** — не `job transition`, а отдельная команда: замечания уходят в тред исполнителя, задача снова running, на проверку она вернётся только с новой версией (другой hash):

```bash
bb agency job return --input-json '{"requestId":"<uuid>","jobId":"<id>","expectedRevision":<revision>,"comment":"Что исправить: …"}'
```

**Запреты сервера** (ошибка вместо «попробую»):
- `agent_inactive` — приостановленному сотруднику нельзя назначить задачу и нельзя его запустить;
- `job_has_live_run` — пока тред попытки может работать, нельзя сменить исполнителя или отдел и нельзя отменить задачу: сначала `launch cancel`;
- `assignee_is_reviewer` — исполнитель не может быть проверяющим своей задачи;
- `self_review` — проверяющему нельзя дать на проверку его собственную работу;
- `member_has_open_jobs` — нельзя убрать из отдела сотрудника с открытыми задачами в нём;
- `duplicate_department_name` — названия отделов не повторяются;
- `spec_required` — `launch prepare` отказывает, если под корнем `new-program` запускается задача отдела из списка «нужна спецификация», а принятой спецификации нет или она не связана с этой задачей. Снять тремя шагами: задача в отделе спецификаций; её приёмка (`done` и принятая текущая версия); `attach-input` этой версии или `job depend` на ту задачу. Пустые `specDepartmentId` / `specGatedDepartmentIds` правило выключают;
- `work_kind_owner_only` — понизить `workKind` с `new-program` может только владелец (вызов без `ctx.caller`); агент получает этот отказ.

Руководитель родительской задачи получает сообщение в свой тред, когда подзадача (своего или другого отдела, в любой папке) переходит в review, waiting_input, blocked, done или canceled. Опрашивать статус циклом не нужно.

Сервер переводит running в blocked сам, с системным комментарием о причине: два напоминания о несданной версии, тред завис без событий, не запустился, застрял в ошибке или упёрся в потолок попытки. Подробно — [Среда исполнения](runtime.md).

## Поручить из чата (диспетчер)

1. **Маршрут.** Мелкое, срочное, вопрос, настройка BB — сделай сам. Многошаговое, с отдельным результатом, нужна проверка, переживёт чат — поручи. Не уверен — одной фразой предложи владельцу.
2. **Отдел.** Сверь фразу с [картой поступления](routing.md) и с [работой отделов](departments.md). Если результат собирают несколько отделов — возьми строку [цепочки](chains.md) и поставь только корень. Затем раздел «Принимаем» выбранного отдела. Агентство добавляет список отделов в инструкции чата; полный текст — `bb agency workspace --json` (`processVersions`). Подходящего нет — не создавай, скажи, какого отдела не хватает. Новая программа или сервис — главная задача в отдел спецификаций с `"workKind":"new-program"`. Багфикс и одна функция в известном модуле — `bugfix` / `feature` сразу в профильный отдел.
   **Смешанный продукт** (пост + обложка, текст + картинка, исследование + макет) — корень в отдел, который **собирает** продукт, с подзадачами в профильные отделы. Не отдавай целиком в первый попавшийся отдел и не жди, что он вернёт бриф владельцу вместо декомпозиции.
   **Большой поток в один отдел.** Каждое поручение — своя оценка. Своё оставляем, чужое — подзадача в принимающий отдел или возврат. L — этапы владельцу. Пачку не глотать и не делать «Не принимаем» своими руками.
   **Проект.** Выбери привязку, где лежит папка твоего окружения (сравни `pwd` с `canonicalRoot`): сотрудник запустится на её машине. Проект не подключён или отключён — поручение не создавай, скажи владельцу подключить папку в разделе «Проекты».
   Сверь папку чата с `bb agency workspace --json`: она должна лежать внутри `canonicalRoot` привязки на этой машине. Привязки нет — скажи владельцу подключить проект (`bb agency project bind`); поручение, дерево папок и привязки не создавай. Одна привязка на проект: отдельную привязку на раздел не заводи. Папка чата внутри раздела BB (`bb project-folders list`: папка с `projectId` этого проекта, чей `path` содержит папку чата; бери самый глубокий) — передай его `id` в `sectionId` поручения.
3. **Бриф.** По шаблону из [Должностные инструкции](job-descriptions.md), раздел 5. Критерий приёмки должен проверяться без автора.
4. **Создай на руководителя отдела:**

   ```bash
   bb agency job create --input-json '{"requestId":"<uuid>","bindingId":"<bindingId>","departmentId":"<departmentId>","assignedAgentId":"<leadAgentId>","title":"…","brief":"…","acceptance":"…","sectionId":"<id раздела или опусти>","workKind":"<new-program|feature|bugfix или опусти>"}'
   ```

   `key` назначит сервер. Необязательно: `priority` (low / normal / high / urgent), `dueAt` (ISO UTC), `parentJobId`, `sectionId`, `workKind` (`new-program` / `feature` / `bugfix`).
5. **Запуск идёт сам.** Создание или назначение исполнителя ставит поручение в очередь запуска; обход каждые 15 секунд вызывает `launch prepare`. Владельца не проси нажимать «Поставить в очередь» или «Запустить». Среда не готова, расходится закрепление навыка или занят слот — задача ждёт в очереди и стартует сама. Живой запуск объявляй только по квитанции `launch prepare`.
6. **Сообщи владельцу:** ключ AG-N, отдел, руководитель; запущено или ждёт среду. Поручённую работу сам не делай.

## Цикл руководителя

Тред запущен на задачу, где ты исполнитель и руководитель отдела.

1. **Оценка на входе — первым действием.** Сверь поручение с регламентом отдела и запиши оценку данными: комментарий с обоснованием (профиль, входы) и тремя references — размер, риск, решение. Оценка показывается в карточке задачи; у запущенной главной задачи без оценки карточка пишет «Оценки на входе нет».

   ```bash
   bb agency job comment --input-json '{"requestId":"<uuid>","jobId":"<id>","comment":"Оценка: наш профиль, входы есть. Две подзадачи: реализация и проверка.","references":[{"type":"intake_size","id":"M"},{"type":"intake_risk","id":"medium"},{"type":"intake_decision","id":"split"}]}'
   ```

   Значения: `intake_size` S / M / L; `intake_risk` low / medium / high; `intake_decision` accept (беру целиком) / split (разбиваю на подзадачи, в том числе в другие отделы) / clarify (нужен ответ владельца) / return (собирать не из чего или нет подходящего отдела). Все три — ровно по одному, иначе сервер отклонит комментарий.
   Если в истории уже есть оценка (в том числе от оценщика) и ты согласен — не пиши вторую; не согласен — запиши свою. Оценщик не создаёт подзадачи и сам не блокирует задачу.
   - Смешанный продукт (часть «Принимаем», часть чужая) — split: подзадачи в отделах, которые принимают эту работу. Сами чужое не делаем.
   - Новая программа или сервис (`workKind` new-program) без принятого предложения — split в отдел спецификаций (Продукт), код не нарезать. Размер L на новой программе — короткий [круглый стол](council.md), затем [предложение](proposal.md), не accept в разработку.
   - Инженерная неопределённость до спецификации: подзадача `workKind: "discovery"` (разведка) или `"spike"` (ограниченный эксперимент) в Разработке с непустыми `contract.mayChange`, `mustNotTouch`, `checks`. Такая подзадача допускается до финальной спецификации; production-реализация остаётся под spec gate. Не передавай инженерный эксперимент продакт-менеджеру.
   - Весь бриф мимо и собирать не из чего — возврат владельцу (раздел «Возврат»).
   - Не хватает входов или решение за владельцем — `report-needs-input`.
   - Размер L — предложи владельцу этапы, не раздувай одну задачу.
   - Пачка поручений сразу: каждое оценить отдельно. Своё оставить, чужое — подзадача в другой отдел или возврат. Пачку не глотать.
2. **Декомпозиция.** Подзадачи с одним результатом и одним исполнителем:

   ```bash
   bb agency job create --input-json '{"requestId":"<uuid>","bindingId":"<папка подзадачи>","departmentId":"<отдел>","parentJobId":"<id главной задачи>","assignedAgentId":"<участник по роли>","title":"…","brief":"…","acceptance":"…"}'
   ```

   Работа другого отдела — подзадача в том отделе на его руководителя. Сообщения о ней приходят так же, как о подзадачах своего отдела. Если под корнем `new-program` создали задачу отдела из списка «нужна спецификация» раньше принятой спецификации, сервер пишет системный комментарий `intake_violation=spec-before-code` в историю подзадачи и корня; создание при этом проходит.

   **Папка подзадачи** (`bindingId`) — по умолчанию папка главной задачи. Другая папка нужна в двух случаях, их перечисляет слой задачи в промпте:
   - «Other folders of this project» — работа идёт в копии проекта на другой машине (плагин Projects & Sections): передай `bindingId` той папки.
   - «Employees … with their own workplace» — у сотрудника рабочее место на своей машине (плагин File Gateway): его подзадача ставится только в папку рабочего места, иначе `workplace_binding_required`.
   Чужой проект — `binding_mismatch`; без нужного плагина — `integration_required`. Проверку рядом с такой работой и зависимости внутри одного дерева задач сервер разрешает сам. Версию-вход из другой папки `attach-input` копирует в папку подзадачи со сверкой хэша (до 6 МБ; больше — через File Gateway).

   **Автоназначение.** Не знаешь, кто свободен, — вместо `assignedAgentId` передай `"assignment": "executor"` или `"reviewer"`: сервер выберет активного сотрудника этого типа на запускаемом CLI с наименьшим числом открытых задач (`"lead"` — руководитель отдела). Нет подходящего — `no_member_for_assignment`.

   **Профиль работы проекта** — поле `workProfileKey`: как в этом проекте делают такой результат (голос, стиль, эталоны). Список профилей виден в слое проекта; поставьте ключ подзадаче, и её исполнитель получит полный профиль и дополнительный критерий приёмки. Нет подходящего профиля — работайте по брифу и скажите об этом в итоге.

   **Контракт исполнения** — граница работы для подзадачи реализации, поле `contract`:

   ```json
   "contract": {"readFirst": ["docs/architecture.md", "src/cards/card.tsx"], "interfaces": ["openCard(id: string): Promise<Card>"], "mayChange": ["src/cards/**"], "mustNotTouch": ["src/billing/**", "публичный API"], "checks": ["npm test", "npm run build"]}
   ```

   `readFirst` — что прочитать до первой правки, `interfaces` — сигнатуры и инварианты, которые результат обязан сохранить, `mayChange` — только файлы этой подзадачи, `mustNotTouch` — что остаётся как есть, `checks` — команды, которые исполнитель прогоняет до сдачи.

   Контракт попадает в промпт запуска и закрепляется в снимке: правка после `launch prepare` делает подготовленный запуск недействительным (`live_job_mismatch`). Изменить — `job update` с новым `contract`, очистить — `"contract": null`.

   **Параллельные подзадачи.** Две задачи одной папки проекта, у которых пересекается `mayChange`, одновременно не запускаются: вторая отвечает `owns_overlap` и ждёт в очереди запуска, пока первая не закончит. Разводи подзадачи по разным файлам или связывай через `job depend`. Разбор конвейера разработки — [Отдел программистов: конвейер](dev-conveyor.md).
3. **Входы.** Результат одной подзадачи для другой передай версией: `bb agency job attach-input` (`targetJobId`, `sourceJobId`, `artifactId`, `version`, `hash`). Ссылка на родителя не даёт доступа к файлам.
4. **Порядок подзадач.** Подзадача, которой нужен результат другой, ждёт её: `bb agency job depend --input-json '{"requestId":"<UUID>","jobId":"<ждёт>","dependsOnJobId":"<должна быть готова>"}'`. Пока зависимость не готова, запуск отвечает `dependencies_open`; назначенная подзадача уже в очереди запуска и стартует сама, когда зависимости будут готовы. Отменённая зависимость снимает задачу с очереди (`dependency_canceled`): реши сам. Убрать — `job undepend`. Циклы сервер не пускает (`dependency_cycle`).
   **Следующий шаг** — работа другого отдела после приёмки: `bb agency job next-step --input-json '{"jobId":"<ранняя задача>","step":{"departmentId":"…","title":"…","brief":"…","acceptance":"…","assignment":"lead"}}'`. Когда ранняя задача станет done, Агентство само создаст задачу рядом с ней (та же папка, тот же родитель), приложит принятые версии и поставит в очередь; итог пишется в историю обеих задач. `step: null` убирает шаг; выполненный шаг не меняется.
5. **Запуск подзадач:** `launch readiness` → `launch prepare`. Реализацию назначай участникам `executor`, проверку — `reviewer`. Проверяющему нельзя передать на проверку его собственную работу: `attach-input` и переназначение вернут `self_review`. Его прежнее заключение как контекст повторной проверки передавать можно.
6. **Реакция на сообщения Агентства:**
   - review — линия закроет станцию сама после ОТК или если ОТК этой роли не нужно. Не жди Accept владельца. `waiting_input` — только если не хватает сырья;
   - blocked с «Возврат» — переназначь (`job update` с `assignedAgentId`), перенеси в подходящий отдел или отмени; живую попытку останови `bb agency launch cancel`;
   - waiting_input — вопрос у владельца, не дублируй;
   - done / canceled — сверь открытые подзадачи.
7. **Дефекты.** Возврат тому же исполнителю или подзадача с `reworkOfJobId: "<id исходной работы>"` и перечнем дефектов, затем повторная проверка. Эти действия расходуют общий лимит одной работы. Независимый следующий компонент создавай без reworkOfJobId. При исчерпании лимита разбери причину; изменение заказа требует решения владельца.
8. **Итог.** Сверь каждую подзадачу. Станции не принимай кнопкой Accept — конвейер закрывает их по версии. Устаревшую версию, заменённую новой, не оставляй в review: отметь замену и отмени устаревшую задачу. Опубликуй сводный отчёт версией главной задачи. Свой итог не принимай: для руководителя линия тоже закроет станцию после публикации.

## Цикл исполнителя

1. **Прочитай слои промпта:** регламент отдела, свою должностную инструкцию, поручение и входные версии (`bb agency job get`).
   - В поручении может стоять блок **«Подсказка к этой работе»**: какие навыки прочитать до начала, какие записи памяти отдела относятся к делу и что открыто под эту задачу из библиотеки отдела. Это подсказка оценщика, а не приказ: бриф, регламент и контракт выше неё. Подсказка не подошла — работай по брифу и скажи об этом в итоговом комментарии, чтобы её поправили.
2. **Сверь с пулом работ до начала.** Не твоё, не хватает входов — возврат. Частично твоё — делай свою часть, остальное перечисли руководителю комментарием.
3. **Работай в границах брифа и контракта.** Не трогай файлы и проекты вне поручения. Есть контракт исполнения — «Нельзя трогать» не меняй, все «Проверки перед сдачей» пройди и перечисли в итоговом комментарии; выйти за границу — вопрос руководителю, не решение. Существенные этапы — короткие комментарии `job comment`: что сделано, чем проверено, что дальше. Не по комментарию на каждое действие.
4. **Самопроверка** по должностной инструкции и критерию приёмки.
5. **Сдача:** отчёт `.agency/jobs/<ключ>/report.md` → `artifact create` и `artifact publish` → итоговый `job comment` для руководителя → завершить ход. Подробно и шаблон отчёта — [Результаты](artifacts.md). Задача перейдёт в review, когда тред станет idle, версия подтвердится hash и есть итоговый комментарий; руководитель получит сообщение.
6. **Не принимай свой результат,** не переводи задачу в done — сервер не даст (`self_acceptance`). Завершил ход без версии или без комментария — придёт напоминание, после лимита задача уйдёт руководителю в blocked.

## Возврат: задача не по профилю

Работа, начатая «на всякий случай», хуже возврата: она тратит бюджет и путает проверку.

**Когда возвращать:**
- поручение из «Не мой пул» должностной инструкции или «Не принимаем» регламента — для исполнителя. Для руководителя смешанный продукт (часть чужая) — не возврат корня, а подзадачи в принимающие отделы; возврат владельцу, только если собирать не из чего или нет подходящего отдела;
- нет обязательного входа из инструкции;
- для выполнения нужна чужая роль (исполнитель получил проверку собственной работы и наоборот).

**Как вернуть:**

1. Комментарий, который руководитель поймёт без переписки:

   ```bash
   bb agency job comment --input-json '{"requestId":"<uuid>","jobId":"<id>","comment":"Возврат: <почему не мой пул — ссылка на пункт инструкции>. Подходит: <роль или отдел>. Чтобы взять, нужно: <что изменить или добавить>."}'
   ```

2. Задачу в blocked (`expectedRevision` — текущая revision из `job get`):

   ```bash
   bb agency job transition --input-json '{"requestId":"<uuid>","expectedRevision":<revision>,"jobId":"<id>","to":"blocked"}'
   ```

3. Заверши ход коротким сообщением «Возвращено руководителю: <причина>». Работу не начинай.

**Кто получает возврат:**
- возврат подзадачи получает руководитель родительской задачи сообщением Агентства;
- главную задачу видит владелец в «Требуют внимания».

Руководитель, получивший главную задачу не по профилю отдела, возвращает её так же и предлагает подходящий отдел.

**Не путать:**
- вопрос по содержанию (что выбрать, какой вариант) — `report-needs-input`, а не возврат;
- противоречие регламента и брифа — тоже вопрос, а не возврат.

## Формат комментария

История задачи показывает комментарии Markdown и сворачивает длинные. Пиши так, чтобы первая строка читалась без раскрытия:

- **Первая строка — итог:** «AG-5 сдана: D1–D3 исправлены, тесты 17/17».
- **Детали — список Markdown.** Переносы в JSON — `\n`: `"comment":"AG-5 сдана: …\n\n- D1 …\n- D2 …"`.
- Ключи задач и версии — только те, что нужны читателю; технические id (`run_…`, `thr_…`, `job_…`) — не в текст, а в `references`, если нужны.
- Больше ~8 строк — это отчёт, а не комментарий: опубликуй версией и дай ссылку.

## Вопрос владельцу

`bb agency job report-needs-input` с `jobId`, `attemptId`, `launchId`, `threadId`, `expectedRevision`, `expectedAttemptRevision` и вопросами, у каждого `sourceRefs`. По желанию у вопроса `choices` (2–4 варианта) — тогда в чате заказчика открываются кнопки. Задача и попытка переходят в waiting_input. Вопросы открывают штатную карточку выбора в чате, откуда ставили задачу (`originThreadId`); не дублируй опрос текстом сообщения. Готовый продукт корня по-прежнему уходит сообщением в тот же чат. После успеха заверши ход сообщением с `waitId`. Продолжение придёт отдельным сообщением в этот же рабочий тред. Не вызывай AskUserQuestion и не держи ход открытым. Если карточки нет — `agency_ask_owner` или `bb agency job ask-owner`.

Новый вопрос после ответа — новый `report-needs-input` с новым `waitId`.

## Зависшая задача (origin-чат)

Если задача `blocked` или `running` без живой попытки висит дольше порога (по умолчанию 1 ч), Агентство пишет в чат постановки (`originThreadId`) и спрашивает **агента этого чата**, не владельца. `waiting_input`, очередь запуска и открытые зависимости не трогает. Без origin — только системный комментарий.

Ответ — `bb agency job stale-answer` с обязательными `nudgeId`, `expectedJobRevision`, `decision` (`close|cancel|keep|escalate`) и `reason`. `close` и `cancel` без опубликованной версии переводят задачу в `canceled` с кодом `closed_by_origin_agent`. `close` при опубликованной версии — отказ `needs_acceptance`. `keep` требует `nextCheckHours` 1–168. Владельца не спрашивать и `agency_ask_owner` не вызывать; `escalate` пишет только во «Входящие».

## Обходчик зависших задач

Тот же механизм, что в [runtime.md](runtime.md#обходчик-зависших-задач). Порог по умолчанию — **1 час** для `blocked` и для `running` без попытки под наблюдателем, включая leftover `running` с тредом `idle` (правила `staleHoursBlocked` / `staleHoursRunning`; `0` = выкл). Повтор 24 ч, максимум 3 попытки. Тихих часов нет.

В origin-чат приходит текст с ключом, состоянием, комментариями, `nudgeId` и командой. Решай сам по чату и карточке.

```
bb agency job stale-answer --input-json '{
  "requestId":"<uuid>","jobId":"<ключ>","nudgeId":"<из сообщения>",
  "expectedJobRevision": <ревизия из сообщения>,
  "decision":"close|cancel|keep|escalate",
  "reason":"…"
}'
```

- `close` / `cancel` без опубликованной версии → `canceled`, код **только** `closed_by_origin_agent`.
- `keep` — задача остаётся, нужен `nextCheckHours` 1–168.
- `escalate` — одно сообщение во Входящие, не в Telegram.
- Отказы: `needs_acceptance`, `revision_conflict`, `foreign_thread`, `duplicate`.
- Не спрашивать владельца. Не вызывать `agency_ask_owner`. `done` не ставить.

## Два критерия приёмки

Сопоставь результат с Job.acceptance и регламентом (ProcessVersion.acceptance). Если оба нельзя выполнить одновременно, процитируй оба источника (processVersion id и job id) и остановись как needs clarification через `report-needs-input`: не auto-pick одного текста, не success, не accept.

## Проверка

1. Открой проверяемую версию с hash (`artifact open` / `artifact versions`), не рабочую копию файла.
2. По каждому критерию: пройдено / не пройдено / не проверено — с командой или местом.
3. Дефект: критерий → место → как воспроизвести → серьёзность.
4. Опубликуй заключение версией своей задачи. Первой строкой отчёта и итогового `job comment` укажи `Вердикт: принять` или `Вердикт: доработать`. Решение о приёмке — у руководителя или владельца.

Принять версию: `bb agency artifact accept` (`jobId`, `artifactId`, `version`, `hash`, `expectedRevision`) — закрывает станцию в review (done в той же транзакции). Владелец не обязан это делать: конвейер принимает сам. Исполнитель свою версию не принимает (`self_acceptance`).


## Исправление сбоев внутри отдела

Сообщение `launch needs the lead's action` — поручение руководителю исправить запуск существующей подзадачи. Прочитайте задачу и исходную работу; уточните конкретный код готовности. При недостающем входе прикрепите существующую опубликованную версию по artifactId/version/hash, при ошибке зависимости или границ файлов исправьте контракт. Не заменяйте подзадачу новой и не запускайте очередной круг документации для исправления одной ссылки. После исправления проверьте readiness: ожидающая очередь продолжит работу автоматически.

Оставьте в задаче причину, сделанное исправление и проверку. Повторно применимый подтверждённый вывод сохраните в знаниях своего отдела (`saveKnowledge`); руководитель вправе принять запись своего отдела через `setKnowledgeStatus`. Предположения остаются предложениями до проверки. Регламент/должностную инструкцию меняйте в пределах текущих полномочий, сохраняя заказ и требования владельца; новая версия применяется к будущим запускам.

Обычные инженерные вопросы решает отдел. Владелец нужен для изменения требований, получения доступа или расширения полномочий. Ошибка движка Агентства требует воспроизведения и отдельной задачи на исправление плагина. [Как читать трассировку](diagnostics.md).
