# Отдел программистов: конвейер

Как собрать отдел, который пишет код по конвейеру «план → разведка → код → проверки → независимая проверка», и как подобрать модели под каждый шаг. Всё держится на обычных возможностях Агентства: подзадачи, контракт исполнения, зависимости, очередь запуска, автопроверка, круги доработки, наблюдение за запуском.

Готовый вариант ставится одной командой: `bb agency kit install --input-json '{"keys":["dev-conveyor"]}'`. Дальше — как это устроено и что менять под себя.

## Роли конвейера

| Роль | Тип роли | Что делает | Чего не делает |
| --- | --- | --- | --- |
| Руководитель (оркестратор) | `lead` | Оценка, разведка, план, контракты подзадач, порядок, сборка итога | Не пишет код, не принимает свой итог |
| Разведчик кода | `executor` | Читает код и документы по вопросу, отдаёт выжимку со ссылками «путь:строка» | Не меняет файлы, не решает, как делать |
| Кодер | `executor` | Пишет и правит код строго внутри контракта, прогоняет проверки контракта | Не выходит за границы, не ослабляет тесты, не делегирует |
| Резервный кодер | `executor` | Берёт подзадачу после двух неудач кодера, отказа его CLI или при риске high | Не меняет контракт, не переписывает всё с нуля |
| Проверяющий кода | `reviewer` | Повторяет проверки, сверяет границы, читает диф, выносит вердикт | Не правит результат, не принимает его |

Дополнительно, если работа того требует: тестировщик браузера (плагин browser-automation), критик плана (проверяющий читает план до старта разработки).

## Модели по видам работы

Правило: планирует и собирает сильная модель, код пишет быстрая, проверяет модель **другого вендора**, чем та, что писала код. Чтение крупных файлов уходит дешёвой модели, чтобы не жечь контекст руководителя.

| Шаг | Что нужно от модели | Пример настройки |
| --- | --- | --- |
| План и сборка | Разбить работу, удержать границы, собрать итог | Claude Fable 5.1 или Opus 5, рассуждение high |
| Разведка и чтение | Быстро прочитать много и коротко пересказать | GPT-5.6-Terra, low, быстрый режим |
| Код | Скорость и дешевизна при чётком контракте | Grok 4.6 (Cursor), medium, быстрый режим |
| Резервный код | Другой вендор, сильнее и настойчивее | GPT-5.6-Sol, high |
| Проверка | Внимательность, другой вендор, чем у кодера | GPT-5.6-Sol, high (или Opus 5) |
| Тест в браузере | Работа с реальной страницей | Claude Sonnet 5, medium, плагин browser-automation |

Модели по умолчанию для новых сотрудников задаются один раз: «Настройки → Правила работы → Новые сотрудники по умолчанию», отдельно для руководителя, исполнителя и проверяющего. В профиле конкретного сотрудника можно поставить любой CLI из `bb provider list` и любую модель из `bb provider models <providerId>`.

## Контракт подзадачи

Контракт — главный инструмент конвейера: он даёт исполнителю контекст и границы, а проверяющему — чек-лист. Заполняет руководитель при создании подзадачи (`bb agency job create`, поле `contract`).

| Поле | Что писать | Зачем |
| --- | --- | --- |
| `readFirst` | Файлы, документы, отчёты прошлых подзадач | Исполнитель не ищет и не догадывается |
| `interfaces` | Сигнатуры, договорённости, инварианты | Результат не ломает соседей |
| `mayChange` | Только файлы этой подзадачи | Параллельная работа без конфликтов |
| `mustNotTouch` | Что должно остаться как есть | Защита от «заодно поправил» |
| `checks` | Команды, которые обязаны пройти | Проверяемая сдача, а не «готово» |

Правила, которые окупаются:

- Одна подзадача — один результат. Не смешивать удаление старого и новую логику: сначала развязка, потом замена.
- Больше 12 строк в `mayChange` — делить подзадачу.
- `mayChange` двух параллельных подзадач не пересекаются. Если пересекаются, Агентство само придержит вторую в очереди запуска (`owns_overlap`) — но лучше развести файлы или связать задачи через `bb agency job depend`.
- Контракт замораживается при запуске. Менять его после подготовки запуска нельзя: это новая подзадача.

## Ход работы

```text
Поручение владельца
  └─ Руководитель: оценка (intake_size, intake_risk, intake_decision)
       ├─ Непонятно, где менять → подзадача «Разведчику кода» → выжимка
       ├─ План: подзадачи кода с контрактами, разные файлы
       │    ├─ Кодер → отчёт: статус, изменённые файлы, критерии, проверки, пробелы
       │    │    └─ Проверяющий: проверки → границы → диф → вердикт
       │    │         └─ Дефекты → доработка тому же кодеру (до трёх кругов)
       │    └─ Две неудачи или отказ CLI → та же подзадача «Резервному кодеру»
       └─ Итог: одна общая проверка (сборка и тесты целиком) + report.md главной задачи
```

Что делает Агентство само, без указаний: создаёт проверку после сдачи (правило «Проверка создаётся автоматически»), держит очередь запуска и лимиты, следит за тредом (тишина, зависание, ошибка провайдера, потолок времени), будит руководителя, когда подзадача закрылась, и считает расход по задаче с подзадачами.

## Отчёт исполнителя

Фиксированные разделы вместо свободного текста — тогда проверяющему есть что сверять, а руководителю не нужно верить на слово:

1. **Статус:** готово / частично.
2. **Что сделано** — коротко.
3. **Изменённые файлы** — списком.
4. **Критерии** — каждый критерий приёмки и доказательство: где смотреть.
5. **Проверки** — таблица: команда, папка, код возврата, результат.
6. **Пробелы** — что не сделано и почему.

«Частично» — нормальный исход. Пустой diff при статусе «готово» — это не готово.

## Порядок проверки

Проверяющий идёт от дешёвого к дорогому и не читает диф, пока не прошли первые два шага:

1. Повторить проверки из контракта, записать вывод.
2. Сверить изменённые файлы с `mayChange` и `mustNotTouch`, проверить `interfaces`.
3. Прочитать диф по критериям приёмки.

Нарушение границ или упавшая проверка — вердикт «доработать» сразу.

## Настройки отдела

| Правило | Где | Для конвейера |
| --- | --- | --- |
| Проверка создаётся автоматически | Правила отдела | Включить: сдача кодера сама уходит проверяющему |
| Проверка у конкретного сотрудника | Карточка сотрудника → «Проверка работы сотрудника» | Выключить у разведчика: его выжимку использует руководитель |
| Кругов доработки | Правила отдела | 3 по умолчанию; дальше решает владелец |
| Мелкие дефекты без нового круга | Правила отдела | Включить, если круги по мелочам дороже пользы |
| Перепроверять принятое за день | Правила отдела | Ночная перепроверка принятых версий проверяющим |
| Одновременных запусков | Лимиты отдела | Держит параллельность кодеров в рамках |
| Запуск без песочницы | Правила отдела, машины или сотрудника | Нужен там, где песочница CLI не пускает команды Агентства |

## Как собрать свой вариант

1. Поставить готовый отдел: `bb agency kit install --input-json '{"keys":["dev-conveyor"]}'`. Сотрудники создаются на своих CLI; если CLI не подключён в BB, сотрудник получает модель роли по умолчанию, и об этом говорит ответ.
2. Или собрать вручную: `bb agency agent create` на каждую роль, `bb agency department create` с регламентом, `bb agency department membership add` с типами ролей.
3. Подогнать модели под свою подписку: `bb agency agent save` с нужными `providerId`, `model`, `reasoningEffort`, `serviceTier`.
4. Проверить готовность проекта: в карточке проекта «Готовность к запуску» — правила проекта, машина, CLI сотрудников, отдел с руководителем.
5. Прогнать одну маленькую задачу целиком и посмотреть расход: `bb agency job usage --input-json '{"rootJobId":"<jobId>"}'`.

## Чего конвейер не делает

- Не запускает команды сам: проверки из контракта выполняет исполнитель и повторяет проверяющий. Агентство сверяет результат по отчётам и версиям, а не по своему прогону.
- Не ведёт ветки и не сливает их: работа идёт в папке проекта, git остаётся за владельцем.
- Не переключает CLI автоматически при отказе провайдера: задача уходит руководителю как заблокированная, и он отдаёт её резервному кодеру.
