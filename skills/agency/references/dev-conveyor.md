# Работа отдела разработки

Цель — завершённое работающее изменение по фиксированным критериям. Опыт: AG-154/AG-161 — ограниченный результат принят без лишних требований; AG-156/AG-158 — лишний круг из-за названия теста; AG-157/AG-159 — зелёные тесты при реальной ошибке; линия AG-177 — сбои входов и поздняя интеграция.

> [!IMPORTANT] Обязательная проверка сохраняется
Ослаблять тесты или считать непроверенный обязательный сценарий успешным нельзя. Убираем повтор принятого без причины и возвраты за необязательную косметику.

## Минимальный процесс

1. Руководитель фиксирует критерии, границы файлов, доступы и живую приёмку. Проверяет команды в нужном окружении.
2. Один исполнитель воспроизводит проблему или проходит малый сквозной сценарий, делает изменение и проверяет затронутое поведение.
3. Независимый проверяющий сверяет точную версию/hash, diff, критерии, доказательства и связанные регрессии.
4. Руководитель принимает результат, завершает необходимую доставку и собирает новый итог после рабочих подзадач.

Разведка нужна для конкретной неопределённости. Новому продукту нужна принятая спецификация; discovery/spike может проверить предположение до неё. Локальная правка не требует нового проекта спецификации. Параллельность — при непересекающемся владении файлами.

| Роль | Ответственность |
| --- | --- |
| Руководитель | Критерии, минимальный план, вмешательство и завершение |
| Исполнитель | Изменение, воспроизведение, доказательства; не принимает себя |
| Проверяющий | Независимый вердикт; не правит результат |
| Помощник/разведчик | Факты, пути, сравнение попыток; без лишних запусков |
| Резервный кодер | По решению после диагностики, без автоматической замены на второй ошибке |
| Тестировщик браузера | Реальный UI-сценарий; без подгонки страницы под PASS |

Модели берутся из `bb provider models <providerId>` с сохранением предпочтений владельца. Пресеты Sol — GPT-6-Sol; Grok без быстрого режима. Alias Opus должен существовать в каталоге.

## Контракт и доказательства

Контракт: `readFirst`, `interfaces`, `mayChange`, `mustNotTouch`, `checks`. Границы должны позволять выполнить критерий; конфликт решает руководитель до запуска. После подготовки контракт не переписывают скрытно. Связанная доработка сохраняет `reworkOfJobId`; копия не обнуляет лимит.

| Критерий | Статус | Версия/hash | Доказательство |
| --- | --- | --- | --- |
| Обязательное поведение | PASS / FAIL / не проверен | Точная версия | Команда/сценарий, окружение, результат |

При доработке сохраняйте доказательства принятых незатронутых критериев. Проверяйте оставшиеся дефекты и связанные регрессии. Полный повтор обоснован изменением общих зависимостей, окружения, недостоверными доказательствами или обязательными правилами проекта; запишите причину. Новое пожелание — отдельная задача. Противоречивый критерий сначала разрешает руководитель.

Неверный результат, потеря данных, безопасность и сломанный обязательный сценарий блокируют приёмку. Название теста и необязательное оформление не создают круг при `minorDefectsWithoutRound:true`. Непроверенный обязательный критерий не становится PASS.

Отчёт: готово/частично; файлы; критерии; команды, папки и коды выхода; установка; остаток. Сдача через `artifact create` → `publish` и итоговый комментарий. Проверяющий публикует `Вердикт: принять` или `Вердикт: доработать`; замечание содержит критерий, место, воспроизведение и серьёзность.

## Вмешательство и обучение

После второго похожего отказа руководитель читает `bb agency job diagnose --input-json '{"jobId":"AG-235","limit":100}' --json`. Старые попытки выбираются через `attemptId`, страницы через `beforeSeq`. Подробнее: [диагностика](diagnostics.md). Сравнивает вердикты, сообщения и trace; определяет причину: код, среда, входы, критерии или конвейер.

После третьего неудачного прохода обычные повторы остановлены. Руководитель использует выданные полномочия. Ремонт собственного конвейера — отдельная работа с регрессионным доказательством и независимой проверкой. `job recover` с причиной, исправлением и результатом **выполненной** проверки разрешает одно продолжение.

Положительное независимое заключение по точной версии может снять устаревший отказ через `artifact accept` с `reviewResolution`, без нового авторского прохода. При отсутствии активного родительского треда система создаёт руководителю задачу восстановления. Владелец нужен для новых полномочий и требований.

| Правило | Значение |
| --- | --- |
| Автопроверка | Включена |
| Кругов доработки | 3, затем разбор руководителем |
| Мелкие дефекты без нового круга | Включено в новых комплектах разработки |
| Ночная перепроверка | Только при обоснованной потребности |
| Обучение | Подтверждённые уроки с задачами, версиями и воспроизведением |

Статус done не доказывает корректную приёмку. Проверяйте новый процесс на малой реальной задаче; отслеживайте время до приёмки, число возвратов, их причины и повторяемость.

Установка: `bb agency kit install --input-json '{"keys":["dev-conveyor"]}'`. Существующий отдел обновляется через профили с `expectedRevision`, сохраняя историю и доступы. Запущенные треды получают новый регламент отдельно.
