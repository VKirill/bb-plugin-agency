# Отдел, сотрудник и инструкции

## Входы

Получить выбранный ProjectBinding, доступные отделы/сотрудников и запрос владельца. Если настройка только проектируется, достаточно описания; отсутствующие ID оставить в списке незаполненного, не создавать фиктивные записи.

## Подготовка отдела

1. Определить название, руководителя (реальный Agent), состав через Membership, связь с проектом через ProjectDepartment.
2. В ProcessVersion.instructions записать: какие задания принимает отдел → этапы → условия передачи между ролями → возврат при дефекте.
3. В ProcessVersion.acceptance записать повторяемый класс результата: схема/validate, публикация через Agency CLI, признаки принятого файла. Не path и не маркер чужой задачи. Конкретный файл и маркер — только Job.acceptance.
4. В reviewPolicy.required указать принятое требование ревью. Job.acceptance дополняет процесс, не отменяет его. Не придумывать поддерживаемые схемой дополнительные поля. Слой задачи не снимает текст отдела.

Текст инструкции отдела:

```text
Принимаем: [класс работ и необходимые входы].
Работа: [этапы; кто делает; выход каждого].
Передача: [получатель, принятая версия, критерии].
При дефекте: [кому вернуть, что исправить, какую проверку повторить].
```

## Подготовка сотрудника

1. Agent задаёт имя/state; AgentVersion — положительный номер version, специализацию и инструкции. Роль не равна модели, а сотрудник не равен BB thread.
2. В instructions записать: зона ответственности → методы → обязательные проверки → границы решений → формат передачи. Не вставлять сюда правила всех отделов и 208 поручений.
3. Выбрать providerId/model из доступной среды, skillIds из `bb agency catalog` (формат `skill_` + 64 hex). Имя навыка и вымышленные skl_* не заменяют ID. Пока MCP в каталоге unavailable — `mcpIds: []`. Не переносить модель из примера как обязательную.
4. Сослаться на реальный policyVersionId; не превращать текст инструкции в выдачу прав. state=active не означает, что сотрудник запущен.

Текст инструкции сотрудника:

```text
Отвечаешь за: [специализация].
На входе проверяешь: [существенные материалы].
Применяешь: [профессиональные методы по условиям].
Сдаёшь: [результат и критерии самопроверки].
Передаёшь дальше: [кому и какие версии/ссылки].
Если не можешь продолжить: [конкретный вопрос/блокер].
```

## Проверка и сохранение

Проверить принадлежность сотрудника отделу и отдела проекту, совместимость процесса с политиками, реальные ссылки на версии. При доступном UI/операции сохранить и перечитать результат. Без инструмента сохранения передать текст для полей, отмеченный как подготовленный, не сохранённый.

Профессиональные навыки (копирайт, SEO, дизайн) — дополнительные методы сотрудника. Основной agency задаёт работу в плагине; model-task-prompts нужен для передачи; agency-artifacts — для оформления файлов. Каталог маршрутов используется только по выбору владельца как пример.

Для первичного создания: `bb agency schema createPolicyVersion|provisionAgent|provisionDepartment`, затем `--input-json`. provisionAgent возвращает Agent и AgentVersion, provisionDepartment — Department, ProcessVersion и Membership руководителя. Не проси внутренние ID заранее. policyVersionId бери из workspace.policies по полному содержимому, не из catalog label. Сохранение профиля: saveAgentProfile / saveDepartmentProfile с expectedRevision, не цепочка createVersion+update. Если CLI недоступен, останься на подготовленном пакете.
