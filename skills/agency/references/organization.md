# Проекты, отделы, руководители и сотрудники

## Как устроено

**Проект — это привязка (ProjectBinding): папка BB-проекта на одной машине.** Поля: `bbProjectId`, `environmentId`, `hostId`, `canonicalRoot`, `policyVersionId`, `sectionId`, `archivedAt`.

- **Где идёт работа.** Сервер BB ставит задачи и хранит историю, а сотрудник запускается на машине привязки и работает с файлами этой папки. Для запуска нужны: хост, подключённый к BB; CLI сотрудника (Claude Code, Codex, Cursor и др.), установленный и авторизованный на этой машине; файл `.bb/AGENTS.md` в папке; политика, разрешающая эту машину.
- **Несколько машин.** Один BB-проект может лежать на нескольких машинах (например Mac mini и OVH). Каждую нужную папку подключают отдельной привязкой: у неё свои задачи и история. Подзадачи живут в привязке родителя.
- **Новый BB-проект** CLI не создаёт — только `project bind` существующего окружения. Одну и ту же папку дважды подключить нельзя.
- **Отключить** (`project archive`): новые задачи, связи и запуски закрыты, история остаётся, вернуть — `project restore`. **Удалить** (`project delete`) можно только привязку без задач; BB-проект и файлы не трогаются.

**Политика прав (PolicyVersion)** — неизменяемая запись: `allowedCapabilities`, `cliHostConstraints` (провайдеры и машины), `secretRefs` (только имена секретов). Права запуска — пересечение политики привязки и политики сотрудника. Текст инструкции прав не даёт. Совпадающую по содержимому политику переиспользуй из `workspace.policies`, новую не плоди.

**Отдел** — Department (`name`, `leadAgentId`, `processVersionId`, `availability`) + регламент ProcessVersion (`instructions`, `acceptance`, `reviewPolicy.required`) + состав Membership с **типом роли**: `lead` / `executor` / `reviewer` / `assistant`.

- Отдел общий для агентства: `availability: all` (по умолчанию) — принимает задачи из любого подключённого проекта, связи не нужны.
- `availability: selected` — только из проектов, связанных через `project link-department`; снять — `project unlink-department`. Ограничить нельзя, пока у отдела открытые задачи в несвязанных проектах.

**Тип роли** — что система делает с участником отдела. Ровно четыре типа:

| Тип | Что делает система | Кого так назначают |
| --- | --- | --- |
| `lead` — руководитель | Получает поручения отдела, создаёт и запускает подзадачи, получает сообщения о них, не получает напоминаний, пока ждёт подзадачи | Руководитель отдела, тимлид, главный редактор |
| `executor` — исполнитель | Делает работу, сдаёт версию, может вернуть задачу | Разработчик, копирайтер, аналитик, дизайнер |
| `reviewer` — проверяющий | Проверяет чужие версии; сервер отклоняет (`self_review`) входную версию его собственной работы и переназначение такой проверки на него | QA, ревьюер кода, редактор, фактчекер |
| `assistant` — помощник | Готовит материал для одного сотрудника отдела: получает только подзадачи, не ведёт главную задачу отдела (`assistant_main_job`), не создаёт поручения (`assistant_cannot_delegate`), не помогает другому помощнику | Разведчик по коду, сборщик ссылок, переводчик черновика |

Тип задаётся в составе отдела, а не в профиле: один сотрудник может быть исполнителем в одном отделе и проверяющим в другом. Старое значение `member` читается как `executor`. Других типов нет: «утверждающий» — проверяющий с правом приёмки, «наблюдатель» — подписка, «директор» — руководитель над отделами.

**Помощники.** У помощника в составе отдела есть поле `helpsAgentId` — кому он помогает; пустое значение делает его общим помощником отдела. У одного сотрудника не больше трёх помощников (`assistant_limit_reached`), помощник не помогает сам себе и другому помощнику. Смысл роли — снять с дорогой модели чтение и сбор: помощник читает файлы и страницы, возвращает выжимку со ссылками, а решения принимает тот, кому он помогает. Модель помощнику по умолчанию — самая дешёвая быстрая из «Настройки → Правила работы → Новые сотрудники по умолчанию».

**Сотрудник** — Agent (`name`, `state`: active / paused / archived) + AgentVersion (`version`, `role`, `instructions`, `providerId`, `model`, `reasoningEffort`, `serviceTier`, `skillIds`, `mcpIds`, `policyVersionId`). `providerId` — любой CLI из `bb provider list`; `model` — из `bb provider models <providerId>`; `serviceTier: "fast"` — быстрый режим; поддерживает ли его CLI, говорит сам BB (`supportsServiceTier` в `bb provider list --json`: на этой машине — Codex, Cursor, OpenCode, Antigravity, но не Claude Code). Политика сотрудника с непустым `providerIds` должна включать его CLI, иначе сохранение отклоняется (`provider_not_allowed_by_policy`). Правка профиля создаёт новую версию. Уже идущие запуски держат снимок старой.

- `role` — **должность**, свободный текст на языке команды: «Разработчик TypeScript», «SEO-специалист», «Head of Engineering». Не тип роли, не модель и не имя; не транслитерируй и не переводи.
- `name` — как сотрудника видит владелец: «Разработчик», «Руководитель SEO».
- `state=active` не значит, что сотрудник запущен.

## Стартовые отделы, архив и удаление

- `bb agency kit list` — каталог стартовых отделов на языке Агентства: офис владельца, продукт, дизайн, разработка (и её конвейер), инфраструктура и безопасность, исследования и аналитика, маркетинг с ветвями SEO, реклама, контент и соцсети, тексты и документация, продажи и клиенты, администрация, автоматизация и агенты: что установлено, на каких CLI задуманы сотрудники и сколько записей можно перевести.
- Отдел `owner-office` — «Офис владельца»: адрес для работы, у которой нет своего отдела, и для сквозных проектов.
- Ветви: `seo`, `ads`, `social` подчиняются `marketing` — при установке подчинённость проставляется сама, если родитель тоже установлен. В каждом отделе каталога есть руководитель, исполнители, проверяющий и помощник на дешёвой быстрой модели. В его «Не принимаем» перечислены остальные отделы, поэтому задача без адреса невозможна.
- Отдел `dev-conveyor` — готовый конвейер разработки с ролями под разные модели: руководитель планирует, разведчик читает, кодер пишет, проверяющий другого вендора проверяет. Разбор — [Отдел программистов: конвейер](dev-conveyor.md).
- `bb agency kit install --input-json '{"keys":["development"],"language":"en"}'` — поставить выбранные отделы с сотрудниками. Сотрудник с заданным CLI получает его, если этот CLI подключён в BB; иначе берётся модель роли из правил по умолчанию, и ответ это называет.
- `bb agency kit translate` — перевести стартовые записи, которые владелец не менял; изменённые остаются.
- Не нужен отдел — `bb agency department archive` (нужны закрытые задачи), вернуть — `department restore`. Удалить без истории — `department delete`.
- Не нужен сотрудник — `bb agency agent save` со `state: archived`; без истории — `agent delete`. Что мешает удалению: `bb agency call recordLifecycle`.

Своя организация не обязана повторять стартовую: отделы, составы, регламенты и правила задаёт владелец.

## Профили работ проекта

Профиль отвечает на вопрос «как в этом проекте делают такой результат»: голос канала, стиль превью, одобренные эталоны, дополнительный критерий приёмки. Он принадлежит BB-проекту, а не папке: у проекта на двух машинах голос один.

- Список профилей приходит в **каждый** запуск проекта: руководитель видит, что у проекта есть, и по признакам узнаёт работу этого вида.
- Полный текст профиля приходит только в ту задачу, которой профиль назначен: `bb agency job update --input-json '{"requestId":"<uuid>","jobId":"<id>","expectedRevision":<n>,"workProfileKey":"tg-post"}'`. Снять — `"workProfileKey": null`.
- Профиль закрепляется в снимке запуска: правка профиля после `launch prepare` на идущую попытку не влияет.
- CLI: `bb agency profile list|save|delete`. Интерфейс: карточка проекта → вкладка «Профили работ».
- Регламенты отделов, которые делают контент («Тексты и документация», «Контент и соцсети», «Дизайн»), требуют профиль или прямое указание владельца во входах — без них работа не начинается.

Пример: у проекта есть `tg-post` (голос канала), `zen-post` (другая стилистика) и `yt-thumbnail` (стиль превью). Владелец пишет «сделай превью к ролику» — руководитель ставит подзадаче `yt-thumbnail`, и дизайнер получает стиль и эталоны, не спрашивая.

## Слои правил

Правила работы наследуются: Агентство → отдел → машина (только «Запуск без песочницы», «Настройки → Машины») → сотрудник. Правило машины нужно, когда песочница там не пускает команды Агентства, например на Linux-сервере.

Руководитель может включить отделу «Перепроверять принятое за день»: раз в сутки после «Часа перепроверки» проверяющий получает задачу с версиями, принятыми после прошлой перепроверки (до 20 за ночь, по одной задаче на папку проекта). Приёмка остаётся в силе, находки решает владелец.

Если одно и то же замечание возвращает работу отдела в трёх задачах за 30 дней, Агентство предлагает запись в знания отдела. Предложение видно в «Знаниях»; принятое идёт в запуски отдела, архивированное больше не предлагается.

Проект → регламент отдела → должностная инструкция → поручение. Каждый нижний слой дополняет верхний и не отменяет его. Все слои доходят до запущенного сотрудника в этом порядке.

ProcessVersion.acceptance — класс результата отдела: схема, обязательные проверки, публикация через Agency CLI. Job.acceptance — точный путь и маркер конкретной задачи. Одно не отменяет другое. Если их нельзя выполнить одновременно, это вопрос владельцу (`report-needs-input` с обоими источниками), а не молчаливый выбор.

## Спроектировать отдел до команд

1. **Результат.** Какой класс результата выдаёт отдел: код с тестами, статья, аудит, дизайн-макет, рекламная кампания.
2. **Зона ответственности.** «Принимаем», «Не принимаем → куда», «Без этих входов не начинаем». Каждая типовая задача компании должна попадать ровно в один отдел.
3. **Роли.** Руководитель (`lead`) + исполнители (`executor`) + проверяющий (`reviewer`), если `reviewPolicy.required`. Без проверяющего руководитель проверяет результат сам по критерию. Одна должность — один сотрудник, пока нет лимитов параллельности. Помощник (`assistant`) нужен там, где исполнителю приходится много читать и собирать: он делает это на дешёвой модели.
4. **Модели.**
   - Руководителю — сильная модель для рассуждений.
   - Исполнителю — по типу работы.
   - Проверяющему — другая модель или провайдер, чем у исполнителя: так проверка независима.
   - Помощнику — самая дешёвая быстрая: он читает и собирает, а не рассуждает.
   - Модель берут из `bb provider models <providerId>`. Если Агентство переносят в другой BB, где этой модели нет, сотрудник встаёт на ближайшую доступную — см. [Среда исполнения](runtime.md), «Модели, которых нет в этом BB».
5. **Тексты.** Регламент отдела и должностные инструкции — по шаблонам [Должностные инструкции](job-descriptions.md).
6. **Сверка.** Руководитель по инструкции может раздать любую задачу из «Принимаем» кому-то из состава. Если нет — не хватает роли.

## Порядок создания

Порядок важен: политика → руководитель → отдел → сотрудники → состав → при необходимости ограничение доступа к проектам.

**0. Прочитай текущее состояние.** `bb agency workspace --json`: привязки, политики, сотрудники, отделы. `bb agency catalog capabilities --json`: `skillIds` (формат `skill_` + 64 hex) и MCP. Провайдер и модель бери у действующих сотрудников или спроси владельца. Не угадывай.

**1. Политика (если подходящей нет).**

```bash
bb agency policy create --input-json '{"requestId":"<uuid>","allowedCapabilities":["read.files"],"cliHostConstraints":{"providerIds":["claude-code"],"hostIds":["<hostId>"]},"secretRefs":[]}'
```

**2. Руководитель.** Роль `lead`, инструкция по шаблону руководителя.

```bash
bb agency agent create --input-json '{"requestId":"<uuid>","name":"Руководитель SEO","state":"active","version":{"version":1,"role":"Руководитель SEO","instructions":"<должностная инструкция>","providerId":"claude-code","model":"<модель>","reasoningEffort":"high","skillIds":["<skill_… agency>"],"mcpIds":[],"policyVersionId":"<policyVersionId>"}}'
```

Навык `agency` нужен каждому сотруднику Агентства: без него агент не знает команд возврата, вопросов и публикации результата.

**3. Отдел.** Руководитель становится участником `lead` автоматически.

```bash
bb agency department create --input-json '{"requestId":"<uuid>","name":"SEO","leadAgentId":"<agentId руководителя>","process":{"instructions":"<регламент отдела>","acceptance":"<класс результата>","reviewPolicy":{"required":true}}}'
```

**4. Сотрудники и состав.** Для каждого: `agent create` с должностью и инструкцией, затем добавь в отдел с типом роли `executor` или `reviewer`:

```bash
bb agency department membership add --input-json '{"requestId":"<uuid>","departmentId":"<departmentId>","agentId":"<agentId>","role":"executor"}'
# помощник: кому помогает — сотрудник этого же отдела
bb agency department membership add --input-json '{"requestId":"<uuid>","departmentId":"<departmentId>","agentId":"<agentId помощника>","role":"assistant","helpsAgentId":"<agentId сотрудника>"}'
```

Сменить тип уже добавленного участника — `department save` с полным списком `memberships`.

**5. Доступ к проектам (по необходимости).** Новый отдел уже доступен во всех проектах. Ограничить выбранными:

```bash
bb agency department availability --input-json '{"requestId":"<uuid>","expectedRevision":<revision отдела>,"departmentId":"<departmentId>","availability":"selected"}'
bb agency project link-department --input-json '{"requestId":"<uuid>","bindingId":"<bindingId>","departmentId":"<departmentId>"}'
```

**6. Проверка.** `bb agency department get --input-json '{"departmentId":"<id>"}'` и `bb agency workspace --json`: руководитель, состав, регламент и доступ к проектам на месте. Затем пробное поручение руководителю (см. [Поручения](job.md)): он должен принять его или обоснованно вернуть.

## Изменение

- **Профиль сотрудника:** `bb agency agent save` — полный профиль, `expectedRevision` = текущий `agent.revision`, `version.version` = текущая версия + 1.
- **Отдел:** `bb agency department save` — полный профиль с `process` и полным списком `memberships`, `expectedRevision` = `department.revision`.
- **Смена руководителя** не переназначает уже идущие задачи: их переназначь явно через `job update`.
- **Архив сотрудника** (`state: archived`) не удаляет его историю и авторство.

## Чего не делать

- Отдел «всё обо всём» или два отдела, принимающих одно и то же.
- Инструкция «ты умный помощник, делай хорошо» без пула работ и границ.
- Копия регламента отдела в каждой должностной инструкции: регламент и так доходит до сотрудника отдельным слоем.
- Руководитель, который сам пишет код или тексты.
- Один и тот же сотрудник — исполнитель и проверяющий.
- Права, секреты или машины, выданные текстом инструкции.
- Фиктивные ID, навыки `skl_…`, модели «из примера».
